## Decisions Made

### Decision: Incremental Delivery Strategy (v0.4.11 and v0.4.12)

**Context**: v0.4.11 roadmap specified 17-21 hours of work including advanced visualisations, property-based testing, and dateparser integration. v0.4.12 roadmap specified 25-30 hours including full migration logic, benchmarking suite, profiling tools.

**Chosen Approach**: Implement core functionality only, defer advanced features

**Alternatives Considered**:
- Full roadmap implementation (would require 40+ hours)
- Skip v0.4.11 and v0.4.12 entirely
- Implement partial features without clear documentation

**Rationale**:
- **Value Focus**: Core temporal reasoning and migration framework provide immediate foundation
- **Resource Management**: Preserve development capacity for higher-priority security improvements
- **Established Pattern**: Match v0.4.11 core approach (proven successful)
- **Risk Mitigation**: Avoid scope creep in massive features
- **Clear Communication**: Comprehensive documentation of what was deferred and why

**ADR Created**: No (implementation decision, not architectural)

### Decision: Zero External Dependencies for Time Parsing

**Context**: v0.4.11 roadmap specified using dateparser library for natural language time expressions

**Chosen Approach**: Manual implementation covering 80% of common use cases

**Alternatives Considered**:
- dateparser library (battle-tested, comprehensive)
- python-dateutil (lighter than dateparser)

**Rationale**:
- **Lightweight**: No additional dependencies (ragged prioritises minimal footprint)
- **Sufficient Coverage**: Manual implementation covers common expressions (yesterday, last week, Q1 2024, January 2024)
- **Full Control**: No surprises from external library behaviour
- **Privacy**: No external parsing service calls
- **YAGNI**: Can add dateparser as optional dependency if user demand emerges

**ADR Created**: No (tactical implementation decision)

### Decision: Placeholder Methods in Migration Framework

**Context**: Backend migration requires backend-specific extraction/loading logic (~1,000 lines per backend)

**Chosen Approach**: Create framework structure with placeholder methods clearly marked

**Alternatives Considered**:
- Implement full ChromaDB extraction/loading logic
- Skip migration feature entirely
- Create incomplete implementation without documentation

**Rationale**:
- **Clear Architecture**: Framework establishes interface contracts
- **Testability**: Validation and structure testable without backend dependencies
- **Extensibility**: Easy to add backend-specific implementations later
- **Documentation**: Placeholders clearly documented as such
- **Honest Communication**: Implementation summary explicitly states 95% deferred

**ADR Created**: No (phased implementation approach)

## Blockers and Challenges

### Challenge 1: Python 3.9 Compatibility Issues

**How Addressed**:
- Discovered system Python was 3.9 despite project requiring 3.12
- Fixed datetime.UTC → datetime.timezone.utc across 5 files
- Fixed union type syntax (T | None → Optional[T]) in 4 files
- Found Python 3.12 in .venv, switched to using .venv/bin/python for tests

**Outcome**:
- All tests passing
- Backward compatibility improved
- Project still requires Python 3.12 (pyproject.toml), but code more tolerant

### Challenge 2: Circular Import Resolution

**How Addressed**:
- Identified circular dependency: memory → retrieval → memory.personalisation
- Implemented lazy loading pattern using __getattr__ in retrieval/__init__.py
- Documented pattern for future similar issues

**Outcome**:
- Import cycle broken
- No performance impact (lazy loading fast)
- Clean solution without restructuring

### Challenge 3: Scope Management for Large Roadmaps
