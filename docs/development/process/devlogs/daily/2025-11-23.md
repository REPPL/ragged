## Decisions Made

### Decision: Defer Integration Tests, Fix Foundation First

**Context**: v0.5.5 roadmap specified integration and E2E testing (12-16h estimated). Upon starting work, discovered test suite completely broken with 489+ import errors and v0.5.3 features completely untested.

**Chosen Approach**: Deviate from roadmap, fix test infrastructure and establish unit test coverage first (~8h actual).

**Alternatives Considered**:
1. Proceed with integration tests despite broken infrastructure (would fail immediately)
2. Fix minimal imports just to make integration tests pass (leaves underlying issues)
3. Fix foundation comprehensively before advanced testing (chosen)

**Rationale**:
- Integration tests impossible with broken test suite
- v0.5.3 features in production with zero tests (quality risk)
- Unit tests prerequisite to meaningful integration tests
- Foundation-first approach saves time long-term

**ADR Created**: No (documented in v0.5.5 implementation and lineage)

---

### Decision: Remove Redundant Metadata from All Documentation

**Context**: Documentation audit revealed 24+ files with metadata (dates, versions, authors) that duplicates information git already tracks, violating Single Source of Truth principle.

**Chosen Approach**: Systematically remove all forbidden metadata, update templates to prevent future violations.

**Alternatives Considered**:
1. Leave metadata as-is (maintains historical "timestamps" in docs)
2. Remove selectively (confusing - some files have it, some don't)
3. Remove all forbidden metadata systematically (chosen)

**Rationale**:
- Git is canonical source for dates, authors, versions
- Metadata in docs creates maintenance burden (becomes stale)
- Potential for inconsistency (doc says one date, git shows another)
- Standards explicitly forbid this metadata

**ADR Created**: No (documented in standards, audit report)

---

### Decision: Simplify README Basic Usage for Beginners

**Context**: README "Basic Usage" section contained 39+ commands across 10 categories, overwhelming for new users. Project already has progressive CLI documentation (Essentials → Intermediate → Advanced).

**Chosen Approach**: Reduce to 12 essential commands covering core workflow, add clear navigation to advanced features.

**Alternatives Considered**:
1. Keep comprehensive command list (overwhelming)
2. Move all commands to CLI docs, minimal README (too minimal)
3. Essential commands + navigation (chosen)

**Rationale**:
- New users need quick start, not comprehensive reference
- Progressive disclosure: essentials in README, advanced in docs
- Aligns with existing CLI Essentials guide (6 core commands)
- Reduces maintenance (advanced features in one place)

**ADR Created**: No (UX decision, not architectural)
