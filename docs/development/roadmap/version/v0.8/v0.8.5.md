# Ragged v0.8.5 Roadmap - Installation Security Hardening

**Status:** Planned

**Total Hours:** 25-35 hours (AI implementation)

**Focus:** Secure installation process, dependency verification, and security-by-default configuration

**Breaking Changes:** None (security improvements only)

**Dependencies:** Requires v0.8.0-v0.8.2 completion (installation foundation)

**Purpose:** Ensure installation process is secure, dependencies verified, secrets managed properly, and system configured with security best practices

---

## Overview

Version 0.8.5 implements comprehensive security hardening for the installation process, addressing supply chain attacks, insecure defaults, secret exposure, and unverified dependencies. This version transforms installation from "functionally correct" to "security hardened."

### Problem Statement

**Current Installation Security Gaps:**
- Dependencies downloaded without verification (checksums, signatures)
- Default configurations insecure (weak secrets, permissive access)
- Secrets generated predictably or exposed in logs
- No pre-install security audit
- Dependency vulnerabilities unknown
- File permissions overly permissive
- Network communication unencrypted
- No verification of installer integrity

### Target Outcomes

**After v0.8.5 Implementation:**
- ✅ All dependencies verified (SHA256 checksums, GPG signatures)
- ✅ Secure defaults enforced (strong secrets, restrictive permissions)
- ✅ Secrets managed securely (never logged, properly encrypted)
- ✅ Pre-install security audit (system hardening recommendations)
- ✅ Dependency vulnerability scanning (CVE database checks)
- ✅ Installer integrity verification (signed installers)
- ✅ Network communication encrypted (TLS/HTTPS)
- ✅ Security documentation and audit logs

## INSTALL-SEC-001: Dependency Verification (5-7 hours)

**Problem:** Dependencies downloaded without verification; vulnerable to supply chain attacks.

**Implementation:**

1. **Design verification system** [1.5-2 hours]
   - Verification methods:
     - **SHA256 checksums:** Verify file integrity
     - **GPG signatures:** Verify authenticity (if available)
     - **HTTPS:** Encrypted downloads (prevent MITM)
   - Checksum storage:
     - Embedded in installer (ragged source)
     - Or fetched from trusted source (verify with signature)
   - Verification pipeline:
     1. Download dependency
     2. Compute SHA256 hash
     3. Compare with expected hash
     4. Verify GPG signature (if available)
     5. Proceed or abort if verification fails

2. **Implement checksum verification** [2-2.5 hours]
   - Create checksum database:
     ```python
     DEPENDENCY_CHECKSUMS = {
         "docker-desktop-mac.dmg": {
             "version": "4.25.0",
             "sha256": "abc123...",
             "url": "https://desktop.docker.com/mac/main/arm64/Docker.dmg",
         },
         "ollama-darwin": {
             "version": "0.1.32",
             "sha256": "def456...",
             "url": "https://ollama.ai/download/Ollama-darwin.zip",
         },
         # ... more dependencies
     }
     ```
   - Verification function:
     ```python
     def verify_download(file_path: str, expected_sha256: str) -> bool:
         sha256 = hashlib.sha256()
         with open(file_path, "rb") as f:
             for chunk in iter(lambda: f.read(4096), b""):
                 sha256.update(chunk)
         computed = sha256.hexdigest()
         if computed != expected_sha256:
             raise SecurityError(f"Checksum mismatch: {computed} != {expected_sha256}")
         return True
     ```
   - Integrate with v0.8.0 installers
   - Block installation if verification fails

3. **Implement GPG signature verification** [1.5-2 hours]
   - Download GPG public keys for vendors:
     - Docker: Import from keyserver
     - Ollama: Fetch from ollama.ai
   - Verify signatures:
     ```bash
     # Import public key
     gpg --import docker-public-key.asc

     # Verify signature
     gpg --verify docker-desktop.dmg.sig docker-desktop.dmg
     ```
   - Python implementation using `gnupg` library
   - Store trusted keys in ragged repository

4. **Add HTTPS enforcement** [0.5-1 hour]
   - All downloads via HTTPS only
   - Reject HTTP redirects
   - Verify TLS certificates
   - Pin certificates for critical dependencies (optional)

5. **Create verification reporting** [0.5-1 hour]
   - Log all verification attempts
   - Report: Which dependencies verified, which failed
   - Display to user during installation
   - Generate verification audit log

**Files:**
- `src/install/security/verification.py` (new - checksum/signature verification, ~300 lines)
- `src/install/security/checksums.py` (new - checksum database, ~200 lines)
- `src/install/security/gpg.py` (new - GPG signature verification, ~200 lines)
- `src/install/installers/base.py` (modify - integrate verification, ~100 lines)
- `tests/install/security/test_verification.py` (new - verification tests, ~300 lines)

**Success Criteria:**
- All dependencies verified before installation
- Verification failures block installation
- GPG signatures validated (when available)
- HTTPS enforced for all downloads
- Verification audit log complete

## INSTALL-SEC-002: Secure Defaults (5-7 hours)

**Problem:** Default configurations insecure; expose ragged to attacks.

**Implementation:**

1. **Design secure configuration defaults** [1.5-2 hours]
   - Security principles:
     - **Least privilege:** Minimal permissions by default
     - **Fail-safe:** Secure defaults, opt-in to less secure
     - **Complete mediation:** All requests checked
     - **Defense in depth:** Multiple security layers
   - Secure defaults:
     - Authentication: **Enabled** by default (disable only with explicit flag)
     - HTTPS: **Enforced** for API/WebUI (self-signed cert if needed)
     - CORS: **Restrictive** (localhost only)
     - File permissions: **User-only** (700 for secrets, 755 for data)
     - Network binding: **localhost only** (no external access)
     - Debug mode: **Disabled** (no verbose logging in production)

2. **Implement secure file permissions** [1.5-2 hours]
   - Set permissions during installation:
     ```python
     import os
     import stat

     # Secrets: User-only read/write (600)
     os.chmod("~/.ragged/.env", stat.S_IRUSR | stat.S_IWUSR)  # 600

     # Config: User-only read/write (600)
     os.chmod("~/.ragged/config.yaml", stat.S_IRUSR | stat.S_IWUSR)  # 600

     # Data directories: User read/write/execute (700)
     os.chmod("~/.ragged/", stat.S_IRWXU)  # 700

     # Logs: User read/write, group/other read (644)
     os.chmod("~/.ragged/logs/", stat.S_IRUSR | stat.S_IWUSR | stat.S_IRGRP | stat.S_IROTH)  # 644
     ```
   - Verify permissions during health checks
   - Warn if permissions too permissive

3. **Implement network security defaults** [1.5-2 hours]
   - Bind to localhost only by default:
     ```yaml
     server:
       host: 127.0.0.1  # NOT 0.0.0.0
       port: 8000
     ```
   - Enforce HTTPS:
     - Generate self-signed certificate if needed
     - Redirect HTTP → HTTPS
     - HSTS header: `Strict-Transport-Security: max-age=31536000`
   - Configure CORS restrictively:
     ```yaml
     cors:
       allow_origins:
         - http://localhost:5173  # SvelteKit dev
         - https://localhost:5173
       allow_credentials: true
     ```
   - Disable debug endpoints in production

4. **Implement authentication by default** [1-1.5 hours]
   - Enable authentication during installation
   - Generate strong admin password (20+ characters, random)
   - Display password once (user must save)
   - Force password change on first login (optional)
   - Provide flag to disable: `--no-auth` (with warning)

5. **Add security warnings** [0.5-1 hour]
   - Warn about insecure configurations:
     - Authentication disabled
     - Binding to 0.0.0.0 (external access)
     - HTTP instead of HTTPS
     - Weak secrets
   - Require explicit confirmation for insecure choices

**Files:**
- `src/config/secure_defaults.py` (new - secure configuration defaults, ~250 lines)
- `src/install/security/permissions.py` (new - file permission management, ~200 lines)
- `src/install/security/network.py` (new - network security config, ~200 lines)
- `src/config/schema.py` (modify - update defaults, ~100 lines)
- `tests/config/test_secure_defaults.py` (new - secure defaults tests, ~250 lines)

**Success Criteria:**
- All defaults secure (authentication on, localhost binding, HTTPS)
- File permissions restrictive (user-only for secrets)
- Network access limited (localhost only)
- Warnings displayed for insecure configurations
- User cannot accidentally create insecure setup

## INSTALL-SEC-003: Secrets Management During Installation (4-6 hours)

**Problem:** Secrets generated predictably, logged, or exposed; vulnerable to theft.

**Implementation:**

1. **Design secure secret generation** [1-1.5 hours]
   - Secrets to generate:
     - JWT signing key (256-bit)
     - Admin password (20+ characters)
     - Database encryption key (if encryption enabled)
     - API keys (for external integrations)
   - Generation requirements:
     - Cryptographically secure random (not `random.randint()`)
     - Sufficient entropy (256 bits minimum)
     - No predictable patterns
     - Unique per installation

2. **Implement secure secret generation** [1.5-2 hours]
   - Use Python `secrets` module:
     ```python
     import secrets
     import string

     def generate_jwt_secret() -> str:
         """Generate cryptographically secure JWT secret."""
         return secrets.token_urlsafe(32)  # 256 bits

     def generate_admin_password() -> str:
         """Generate strong admin password."""
         alphabet = string.ascii_letters + string.digits + string.punctuation
         password = ''.join(secrets.choice(alphabet) for _ in range(24))
         return password

     def generate_api_key() -> str:
         """Generate API key."""
         return secrets.token_urlsafe(32)
     ```
   - Validate strength (entropy check)
   - Never use hardcoded or predictable secrets

3. **Implement secure secret storage** [1.5-2 hours]
   - Store secrets in `.env` file (never committed to git)
   - Set restrictive permissions: 600 (user-only read/write)
   - Optional: Encrypt secrets at rest (using system keyring)
     - Linux: `libsecret` (GNOME Keyring)
     - macOS: Keychain
     - Windows: Credential Manager
   - Load secrets from environment variables (12-factor app)

4. **Prevent secret exposure** [0.5-1 hour]
   - Never log secrets:
     ```python
     # BAD
     logger.info(f"JWT secret: {jwt_secret}")

     # GOOD
     logger.info("JWT secret loaded successfully")
     ```
   - Redact secrets in error messages
   - Mask secrets in configuration display:
     ```
     JWT Secret: ********
     Admin Password: ********
     ```
   - Prevent secrets in system process list (avoid command-line args)

**Files:**
- `src/install/security/secrets.py` (new - secret generation, ~250 lines)
- `src/config/secrets_store.py` (new - secure secret storage, ~200 lines)
- `src/utils/redaction.py` (new - secret redaction, ~150 lines)
- `tests/install/security/test_secrets.py` (new - secrets tests, ~250 lines)

**Success Criteria:**
- Secrets generated with cryptographic randomness
- Secrets stored securely (restrictive permissions)
- Secrets never logged or exposed
- Optional keyring integration works
- Entropy validation ensures strength

## INSTALL-SEC-004: Security Audit Automation (5-7 hours)

**Problem:** No pre-install security audit; users deploy on insecure systems.

**Implementation:**

1. **Design security audit framework** [1.5-2 hours]
   - Audit categories:
     - **System hardening:** Firewall, SELinux, updates
     - **Network security:** Open ports, exposed services
     - **User permissions:** Root usage, sudo access
     - **Filesystem security:** Permissions, encryption
     - **Dependency security:** Known vulnerabilities
   - Severity levels:
     - **CRITICAL:** Must fix before installation
     - **HIGH:** Should fix (warn but allow proceed)
     - **MEDIUM:** Recommend fixing
     - **LOW:** Informational

2. **Implement system hardening checks** [1.5-2 hours]
   - **Firewall status:**
     - Linux: Check `ufw`, `firewalld` active
     - macOS: Check macOS firewall enabled
     - Windows: Check Windows Firewall enabled
   - **SELinux status (Linux):**
     - Check: `getenforce` returns `Enforcing` or `Permissive`
     - Warn if disabled
   - **System updates:**
     - Check last update date
     - Warn if >30 days since last update
   - **Root/sudo usage:**
     - Warn if installing as root (should use regular user)
     - Check if sudo passwordless (security risk)

3. **Implement network security checks** [1.5-2 hours]
   - **Open ports scan:**
     - Scan common ports: 22 (SSH), 80 (HTTP), 443 (HTTPS), 3306 (MySQL), etc.
     - Warn if sensitive services exposed
   - **Exposed services:**
     - Check Docker daemon exposed (`-H tcp://0.0.0.0:2375`)
     - Check Redis/MongoDB without authentication
   - **Firewall rules:**
     - Verify ragged ports (8000, 5173, 8001) not publicly accessible

4. **Implement filesystem security checks** [0.5-1 hour]
   - **Encryption status:**
     - Linux: Check LUKS encryption
     - macOS: Check FileVault enabled
     - Windows: Check BitLocker enabled
   - **Sensitive file permissions:**
     - Check `/etc/passwd`, `/etc/shadow` permissions
     - Check SSH keys not world-readable

5. **Generate security audit report** [1-1.5 hours]
   - Comprehensive report:
     ```
     🔒 Security Audit Report

     System Hardening:
     ✅ Firewall: Active (ufw)
     ⚠️  SELinux: Disabled (recommend enabling)
     ✅ System updates: Last updated 5 days ago

     Network Security:
     ✅ No sensitive services exposed
     ✅ Ragged ports not publicly accessible

     Filesystem Security:
     ⚠️  Disk encryption: Disabled (recommend enabling)
     ✅ Sensitive files properly protected

     Overall Security Score: 8/10 (Good)

     Recommendations:
     1. Enable SELinux: sudo setenforce 1
     2. Enable disk encryption (LUKS)

     Proceed with installation? [Y/n]:
     ```
   - Allow user to proceed or abort
   - Save audit log to `~/.ragged/security-audit.log`

**Files:**
- `src/install/security/audit/framework.py` (new - audit framework, ~250 lines)
- `src/install/security/audit/system.py` (new - system hardening checks, ~300 lines)
- `src/install/security/audit/network.py` (new - network security checks, ~250 lines)
- `src/install/security/audit/filesystem.py` (new - filesystem checks, ~200 lines)
- `src/install/security/audit/report.py` (new - audit reporting, ~200 lines)
- `tests/install/security/audit/` (new - audit tests, ~400 lines)

**Success Criteria:**
- Security audit detects common misconfigurations
- Critical issues block installation
- Warnings allow informed decision
- Audit report actionable (specific fix commands)
- Audit log saved for compliance

## INSTALL-SEC-005: Vulnerability Scanning (4-6 hours)

**Problem:** Dependency vulnerabilities unknown; may install insecure software.

**Implementation:**

1. **Design vulnerability scanning system** [1-1.5 hours]
   - Vulnerability databases:
     - **National Vulnerability Database (NVD):** CVE database
     - **GitHub Advisory Database:** GitHub security advisories
     - **PyPI Advisory Database:** Python package vulnerabilities
   - Scanning approach:
     - Scan Python dependencies: `pip-audit` or `safety`
     - Scan Docker images: `trivy` or `grype`
     - Scan Ollama (manual CVE checks)
   - Severity levels: Critical, High, Medium, Low

2. **Implement Python dependency scanning** [1.5-2 hours]
   - Use `pip-audit` tool:
     ```bash
     pip-audit --desc --format json
     ```
   - Parse results:
     ```python
     vulnerabilities = {
         "cryptography": [
             {
                 "id": "CVE-2023-1234",
                 "severity": "HIGH",
                 "fixed_version": "41.0.5",
                 "description": "..."
             }
         ]
     }
     ```
   - Block installation if critical vulnerabilities found
   - Suggest upgrading packages

3. **Implement Docker image scanning** [1.5-2 hours]
   - Use `trivy` scanner:
     ```bash
     trivy image chromadb/chroma:latest --severity CRITICAL,HIGH --format json
     ```
   - Parse results and report vulnerabilities
   - Suggest alternative images if vulnerabilities found

4. **Create vulnerability report** [0.5-1 hour]
   - Generate report:
     ```
     🛡️ Vulnerability Scan Report

     Python Dependencies:
     ⚠️  cryptography 41.0.3: CVE-2023-1234 (HIGH)
         Fix: Upgrade to 41.0.5 or later
         pip install --upgrade cryptography

     Docker Images:
     ✅ chromadb/chroma:latest: No critical vulnerabilities

     Proceed with installation? [Y/n]:
     ```
   - Save to `~/.ragged/vulnerability-scan.log`

**Files:**
- `src/install/security/vuln_scan.py` (new - vulnerability scanning, ~300 lines)
- `src/install/security/cve_database.py` (new - CVE database queries, ~200 lines)
- `.github/workflows/security-scan.yml` (new - CI/CD vulnerability scanning, ~150 lines)
- `tests/install/security/test_vuln_scan.py` (new - scanning tests, ~200 lines)

**Success Criteria:**
- All dependencies scanned for vulnerabilities
- Critical vulnerabilities block installation
- High/Medium vulnerabilities warned
- Fix suggestions provided
- Scan results logged

## Known Risks

- **Certificate costs:** Code signing certificates expensive ($99-$500/year) (mitigate: budget appropriately, consider Let's Encrypt for TLS)
- **User friction:** Security measures may frustrate users (mitigate: clear documentation, good defaults)
- **False positives:** Vulnerability scanners may report false positives (mitigate: manual review, whitelist known safe issues)
- **Performance overhead:** Security checks add installation time (mitigate: optimize, run in parallel)
