# Ragged v0.8.2 Roadmap - Post-Launch Refinements & Error Recovery

**Status:** Planned

**Total Hours:** 15-25 hours (AI implementation)

**Focus:** Robust error recovery, upgrade paths, and installation refinements

**Breaking Changes:** None

**Dependencies:** Requires v0.8.0-v0.8.1 completion (installation foundation and wizard)

**Purpose:** Transform installation from "works in ideal conditions" to "recovers gracefully from all failures" with comprehensive error diagnostics and automated recovery

---

## Overview

Version 0.8.2 refines the installation experience based on real-world usage, adding comprehensive error diagnostics, automated recovery strategies, improved health checks, seamless upgrade paths, and clean uninstallation. This version addresses the "it broke, now what?" scenarios that emerge after v0.8.0-v0.8.1 deployment.

### Problem Statement

**Current Installation Issues (Post-v0.8.1):**
- Errors encountered with cryptic messages: "Connection refused", "Permission denied"
- No automated recovery from common failures (port conflicts, disk full, service crashes)
- Manual intervention required for most issues
- Upgrading between versions unclear
- No clean way to uninstall ragged
- Health checks detect failures but don't diagnose root causes
- User stuck when installation fails midway

### Target Outcomes

**After v0.8.2 Implementation:**
- ✅ Comprehensive error diagnostic system (identifies root cause)
- ✅ Automated recovery strategies (fixes 80%+ of common issues)
- ✅ Improved health checks (proactive issue detection)
- ✅ Seamless upgrade path (v0.X → v0.Y)
- ✅ Clean uninstall (removes all traces)
- ✅ Self-healing installation (detects and fixes drift)
- ✅ Detailed troubleshooting guidance

## REFINE-001: Error Diagnostic System (4-6 hours)

**Problem:** Errors provide insufficient information; users don't know how to fix issues.

**Implementation:**

1. **Design diagnostic framework** [1-1.5 hours]
   - Error categories:
     - **Connectivity:** Port conflicts, network issues, firewall blocks
     - **Permissions:** File access denied, sudo required, SELinux blocks
     - **Resources:** Disk full, out of memory, CPU exhaustion
     - **Dependencies:** Missing libraries, version conflicts, corrupted installs
     - **Configuration:** Invalid settings, missing values, syntax errors
     - **Services:** Failed starts, crashes, deadlocks
   - Diagnostic pipeline:
     1. Detect error (exception, failed command, health check failure)
     2. Classify error category
     3. Run targeted diagnostics
     4. Identify root cause
     5. Suggest fix
     6. Optionally auto-fix

2. **Implement connectivity diagnostics** [1-1.5 hours]
   - **Port conflict detection:**
     - Identify process using port: `lsof -i :8000` (Linux/macOS), `netstat` (Windows)
     - Suggest killing process or using alternative port
     - Show command to free port: `kill -9 <PID>`
   - **Network diagnostics:**
     - Test localhost connectivity: `ping 127.0.0.1`
     - Check DNS resolution: `nslookup localhost`
     - Verify loopback interface up: `ip addr show lo`
   - **Firewall diagnostics:**
     - Detect firewall software (ufw, firewalld, Windows Firewall)
     - Check if ports blocked
     - Suggest firewall rules: `sudo ufw allow 8000/tcp`

3. **Implement permission diagnostics** [1-1.5 hours]
   - **File permission issues:**
     - Check directory ownership: `ls -la ~/.ragged/`
     - Detect root-owned files (common mistake)
     - Suggest fixing permissions: `sudo chown -R $USER:$USER ~/.ragged/`
   - **Execution permission issues:**
     - Check binary executable: `ls -la /usr/local/bin/ragged`
     - Suggest adding execute permission: `chmod +x /usr/local/bin/ragged`
   - **SELinux diagnostics (Linux):**
     - Check SELinux status: `getenforce`
     - Detect SELinux denials: `ausearch -m avc -ts recent`
     - Suggest SELinux policy changes or disable temporarily

4. **Implement resource diagnostics** [0.5-1 hour]
   - **Disk space issues:**
     - Check available space: `df -h ~/.ragged/`
     - Identify large files: `du -sh ~/.ragged/*`
     - Suggest cleanup: `ragged cleanup --cache` or `docker system prune`
   - **Memory issues:**
     - Check available RAM: `free -h` (Linux), `vm_stat` (macOS)
     - Detect out-of-memory kills: `dmesg | grep -i "out of memory"`
     - Suggest increasing swap or reducing model size

5. **Create diagnostic reports** [0.5-1 hour]
   - Generate comprehensive diagnostic report:
     ```
     Error: ChromaDB failed to start

     🔍 Diagnostics:
     - Port 8001: CONFLICT (process: node, PID: 12345)
     - Disk space: 1.2GB available (5GB recommended)
     - Memory: 4.5GB available (8GB recommended)

     🛠️ Suggested Fixes:
     1. Free port 8001:
        kill -9 12345
     2. Free disk space:
        ragged cleanup --old-logs
        docker system prune
     3. Retry installation:
        ragged install --resume

     📖 Detailed troubleshooting: https://ragged.ai/docs/troubleshooting#chromadb-start-failure
     ```
   - Include system information (OS, version, architecture)
   - Attach relevant log excerpts
   - Provide shareable diagnostic ID for support

**Files:**
- `src/install/diagnostics/framework.py` (new - diagnostic pipeline, ~250 lines)
- `src/install/diagnostics/connectivity.py` (new - network diagnostics, ~200 lines)
- `src/install/diagnostics/permissions.py` (new - permission diagnostics, ~200 lines)
- `src/install/diagnostics/resources.py` (new - resource diagnostics, ~150 lines)
- `src/install/diagnostics/report.py` (new - diagnostic reports, ~200 lines)
- `tests/install/diagnostics/` (new - diagnostics tests, ~300 lines)

**Success Criteria:**
- Diagnostics identify root cause in 80%+ of failures
- Suggested fixes resolve issues without manual intervention
- Diagnostic reports actionable (specific commands)
- Reports generated in <5 seconds

## REFINE-002: Automated Recovery Strategies (5-7 hours)

**Problem:** Detected issues require manual intervention; no automated recovery exists.

**Implementation:**

1. **Design recovery framework** [1.5-2 hours]
   - Recovery strategy types:
     - **Automatic:** Fix applied immediately (safe, non-destructive)
     - **Prompt:** Ask user consent before fixing
     - **Manual:** Provide instructions (cannot automate)
   - Recovery actions:
     - Restart services
     - Clear caches
     - Recreate directories
     - Update permissions
     - Kill conflicting processes
     - Download missing files
     - Repair corrupted databases
   - Rollback capability if recovery fails

2. **Implement service recovery** [1.5-2 hours]
   - **Restart crashed services:**
     - Detect service down: Health check fails
     - Attempt restart: `docker-compose restart chromadb`
     - Wait for health check to pass
     - Retry up to 3 times
     - If still failing, escalate to diagnostics
   - **Recover from corrupted state:**
     - Detect: ChromaDB reports corruption
     - Backup current state: `cp -r ~/.ragged/chromadb ~/.ragged/chromadb.backup`
     - Reinitialize database
     - Offer to restore from backup
   - **Handle dependency updates:**
     - Detect: Ollama/Docker updated, ragged incompatible
     - Suggest: `ragged upgrade` to compatible version

3. **Implement filesystem recovery** [1-1.5 hours]
   - **Fix permissions automatically:**
     - Detect: Permission denied errors
     - Fix: `chown -R $USER:$USER ~/.ragged/`
     - Verify: Retry operation
   - **Recreate missing directories:**
     - Detect: Directory missing (deleted accidentally)
     - Recreate: `mkdir -p ~/.ragged/{documents,cache,logs}`
     - Restore permissions
   - **Clear corrupted caches:**
     - Detect: Cache read errors
     - Clear: `rm -rf ~/.ragged/cache/*`
     - Reinitialize cache

4. **Implement configuration recovery** [1-1.5 hours]
   - **Validate and repair config files:**
     - Detect: Invalid YAML, missing keys
     - Backup: `cp config.yaml config.yaml.backup`
     - Repair: Merge with default config template
     - Prompt user to review changes
   - **Regenerate secrets:**
     - Detect: Missing or exposed JWT secret
     - Generate new secret
     - Update .env file
     - Restart services

5. **Add recovery logging and reporting** [0.5-1 hour]
   - Log all recovery attempts
   - Track success/failure rates
   - Generate recovery report:
     ```
     🔧 Automatic Recovery Applied

     Issue: ChromaDB failed to start (port conflict)
     Action: Killed process 12345 using port 8001
     Result: ✅ ChromaDB now running

     Time: 3 seconds
     ```

**Files:**
- `src/install/recovery/framework.py` (new - recovery pipeline, ~250 lines)
- `src/install/recovery/services.py` (new - service recovery, ~300 lines)
- `src/install/recovery/filesystem.py` (new - filesystem recovery, ~200 lines)
- `src/install/recovery/configuration.py` (new - config recovery, ~200 lines)
- `src/install/recovery/report.py` (new - recovery reports, ~150 lines)
- `tests/install/recovery/` (new - recovery tests, ~350 lines)

**Success Criteria:**
- Automated recovery succeeds in 80%+ of common failures
- Recovery actions safe (no data loss)
- User consent obtained for destructive actions
- Rollback works if recovery fails
- Recovery time <30 seconds (average)

## REFINE-003: Health Check Improvements (2-3 hours)

**Problem:** Health checks detect failures but don't provide context or recommendations.

**Implementation:**

1. **Enhance health check granularity** [1-1.5 hours]
   - Service health levels:
     - **Healthy:** All checks pass, performance good
     - **Degraded:** Functional but slow, warnings present
     - **Unhealthy:** Critical failures, service unusable
   - Check categories:
     - **Connectivity:** Service reachable
     - **Performance:** Response time acceptable
     - **Functionality:** Core features working
     - **Resources:** Sufficient disk, memory
   - Example:
     ```
     Service: ChromaDB
     Status: DEGRADED
     - Connectivity: ✅ Reachable (http://localhost:8001)
     - Performance: ⚠️ Slow (450ms response, >200ms threshold)
     - Functionality: ✅ Query successful
     - Resources: ⚠️ Disk space low (2.1GB available, 5GB recommended)
     ```

2. **Add proactive health monitoring** [0.5-1 hour]
   - Periodic health checks (every 5 minutes)
   - Detect issues before user encounters them
   - Alert user of degradation
   - Suggest preemptive actions (cleanup, restart)
   - Background monitoring (optional, opt-in)

3. **Implement health dashboard** [0.5-1 hour]
   - `ragged health` command with rich output
   - Real-time service status
   - Historical health trends (if monitoring enabled)
   - Quick actions: Restart service, clear cache, view logs

**Files:**
- `src/health/checks.py` (modify - enhance granularity, ~150 lines)
- `src/health/monitoring.py` (new - proactive monitoring, ~200 lines)
- `src/cli/commands/health.py` (modify - dashboard, ~150 lines)
- `tests/health/` (modify - health tests, ~100 lines)

**Success Criteria:**
- Health checks detect degradation before failure
- Health levels accurate (matches user experience)
- Dashboard provides actionable information
- Proactive monitoring reduces unexpected failures

## REFINE-004: Upgrade & Migration Paths (3-4 hours)

**Problem:** Upgrading ragged versions unclear; no migration for config/database schema changes.

**Implementation:**

1. **Design upgrade system** [1-1.5 hours]
   - Upgrade strategies:
     - **In-place:** Update existing installation (default)
     - **Clean install:** Remove old, install new (if in-place fails)
     - **Side-by-side:** Install new alongside old (for testing)
   - Version compatibility matrix
   - Database schema migrations (Alembic or similar)
   - Configuration migrations (add/remove keys)
   - Rollback capability

2. **Implement upgrade command** [1-1.5 hours]
   - `ragged upgrade [version]`:
     - Check current version: `ragged --version`
     - Fetch latest version from PyPI/GitHub
     - Backup current installation
     - Run pre-upgrade checks (disk space, compatibility)
     - Install new version
     - Run migrations (database, config)
     - Verify new version works
     - Remove old version
   - Handle failure: Rollback to backup
   - Support version pinning: `ragged upgrade v0.8.2`

3. **Implement database migrations** [0.5-1 hour]
   - Detect schema changes between versions
   - Apply migrations automatically
   - Backup before migration
   - Validate migration success
   - Rollback if validation fails

**Files:**
- `src/upgrade/upgrade.py` (new - upgrade logic, ~300 lines)
- `src/upgrade/migrations/` (new - database migrations, ~200 lines)
- `src/cli/commands/upgrade.py` (new - upgrade CLI, ~150 lines)
- `tests/upgrade/` (new - upgrade tests, ~250 lines)

**Success Criteria:**
- Upgrades succeed >95% of the time
- Data preserved during upgrades
- Rollback works if upgrade fails
- Upgrade time <5 minutes
- Clear upgrade documentation

## REFINE-005: Uninstall Capability (2-3 hours)

**Problem:** No clean way to remove ragged; users must manually delete files and services.

**Implementation:**

1. **Design uninstall system** [0.5-1 hour]
   - Uninstall options:
     - **Complete:** Remove everything (services, data, config)
     - **Keep data:** Remove services/binaries but keep ~/.ragged/
     - **Purge:** Nuclear option, remove all traces
   - User confirmation required
   - Backup option before uninstall

2. **Implement uninstall logic** [1-1.5 hours]
   - `ragged uninstall [--keep-data] [--purge]`:
     - Stop all services (Docker containers, Ollama)
     - Remove Docker containers and volumes
     - Remove ragged binary/package: `pip uninstall ragged`
     - Remove configuration files (unless --keep-data)
     - Remove data directory (unless --keep-data)
     - Clean up PATH modifications
     - Remove shortcuts/launchers
   - Display what will be removed (dry run)
   - Require explicit confirmation
   - Generate uninstall report

3. **Add backup before uninstall** [0.5-1 hour]
   - Offer to backup data before uninstall
   - Create tarball: `~/.ragged-backup-<timestamp>.tar.gz`
   - Display backup location
   - Suggest how to restore if needed

**Files:**
- `src/install/uninstall.py` (new - uninstall logic, ~250 lines)
- `src/cli/commands/uninstall.py` (new - uninstall CLI, ~150 lines)
- `tests/install/test_uninstall.py` (new - uninstall tests, ~150 lines)

**Success Criteria:**
- Uninstall removes all traces (verified with fresh scan)
- User data preserved if --keep-data specified
- Backup created successfully
- Uninstall time <2 minutes
- Clear warnings before destructive actions

## Known Risks

- **Recovery complexity:** Automated fixes may introduce new issues (mitigate: comprehensive testing, rollback capability)
- **Upgrade failures:** Schema migrations may fail on edge cases (mitigate: backup before upgrade, rollback support)
- **Platform variations:** Recovery strategies may not work on all platforms (mitigate: platform-specific handlers)
- **Data loss:** Aggressive cleanup may delete user data (mitigate: backups, confirmation prompts)
