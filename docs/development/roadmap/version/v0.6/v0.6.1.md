## Features

### OPTIMISE-001: Query Classification System (20-25 hours)

**Purpose:** Analyse queries to determine characteristics for intelligent routing and optimisation.

#### Classification Dimensions

**1. Query Type Detection:**
- **Factual** - Lookup queries ("What is RAG?", "Who invented...")
- **Conceptual** - Explanation queries ("How does RAG work?", "Explain...")
- **Exploratory** - Discovery queries ("Find examples of...", "Show me...")
- **Multi-hop** - Complex reasoning ("Compare X and Y, then...")

**2. Complexity Scoring:**
- **Simple** (1-2) - Single-hop, direct lookup
- **Medium** (3-5) - Multiple concepts, some reasoning
- **Complex** (6-8) - Multi-hop, synthesis required
- **Very Complex** (9-10) - Deep analysis, multiple documents

**3. Intent Classification:**
- **Lookup** - Finding specific information
- **Analysis** - Understanding relationships or patterns
- **Comparison** - Evaluating alternatives or similarities
- **Synthesis** - Creating new insights from multiple sources

**Phase 1: Core Classification Logic (8-10h)**

#### API Design

```python
from src.optimisation import QueryClassifier, RoutingMetadata

# Initialise classifier
classifier = QueryClassifier()

# Classify query
query = "How does ColPali compare to traditional OCR for document understanding?"
classification = classifier.classify(query)

# Access classification results
print(classification.query_type)      # "comparison"
print(classification.complexity)      # 7
print(classification.intent)          # "analysis"
print(classification.is_multi_hop)    # True
print(classification.domain_hints)    # ["vision", "embeddings"]

# Get routing metadata
metadata = RoutingMetadata.from_classification(classification)
print(metadata.recommended_model)     # "llama3.2:70b" (complex query)
print(metadata.estimated_latency_ms)  # 2500
print(metadata.requires_vision)       # True
```

### SECURITY-001: Enhanced MIME Type Validation (2-4 hours) ⭐ HIGH PRIORITY

**Purpose:** Replace basic magic byte detection with robust python-magic library for comprehensive file type validation.

**Audit Reference:** [v0.6.0 Security Audit](../../../../audit/security/baseline/v0.6.0-security-audit.md) Section 3.2 H-3, CR-SEC-001

#### Problem Statement

Current MIME type validation (`src/utils/security.py:98-155`) uses basic magic byte detection with only 8-byte header inspection. This has limitations:
- Limited signature database (only 6-7 file types)
- No deep inspection (exploits can hide beyond first 8 bytes)
- ZIP-based formats treated generically (potential for macro exploits)

#### Implementation Phases

**Phase 1: python-magic Integration (1-2h)**
- Add `python-magic>=0.4.27` dependency to pyproject.toml
- Rewrite `validate_mime_type()` function with python-magic
- Implement graceful fallback to basic detection if unavailable
- Update file upload endpoint to use new validation

**Phase 2: Testing & Validation (1-2h)**
- Comprehensive test suite for MIME validation
- Tests for: PDF, TXT, HTML, renamed executables, ZIP bombs
- Integration tests with file upload endpoint
- Edge case testing (empty files, corrupted headers)

#### Success Criteria

- [ ] python-magic dependency added and documented
- [ ] validate_mime_type() rewritten with robust detection
- [ ] 100% test coverage for MIME validation
- [ ] Tests pass for all supported file types
- [ ] Tests detect and reject renamed executables
- [ ] Graceful fallback implemented for backwards compatibility
- [ ] Documentation updated with installation instructions

#### Files Changed

- `pyproject.toml` - Add python-magic dependency
- `src/utils/security.py` - Enhanced MIME validation
- `src/web/api.py` - Use enhanced validation in upload endpoint
- `tests/security/test_mime_validation.py` - Comprehensive test suite

### SECURITY-002: Fix Path Validation Test Failures (4-8 hours) ⭐ HIGH PRIORITY

**Purpose:** Fix failing path validation tests to ensure comprehensive protection against path traversal attacks.

**Audit Reference:** [v0.6.0 Security Audit](../../../../audit/security/baseline/v0.6.0-security-audit.md) Section 6.2, CR-SEC-002

#### Problem Statement

Four path validation tests are failing, indicating potential edge cases in path traversal prevention:
```
FAILED test_path_validation.py::TestPathValidator::test_validate_safe_relative_path
FAILED test_path_validation.py::TestPathValidator::test_validate_path_outside_base_rejected
FAILED test_path_validation.py::TestPathValidator::test_validate_symlink_blocked_when_not_allowed
FAILED test_path_validation.py::TestConvenienceFunctions::test_validate_path_convenience_function
```

These failures suggest issues with:
1. Relative path handling
2. Base directory constraint enforcement
3. Symlink validation
4. Convenience function implementation

#### Implementation Phases

**Phase 1: Investigation & Diagnosis (1-2h)**
- Run failing tests with verbose output to identify root causes
- Review `validate_file_path()` implementation in src/utils/security.py
- Review `validate_path()` implementation in src/utils/validation.py
- Analyse symlink handling and relative path resolution logic

**Phase 2: Fix Implementation (2-4h)**
- Fix relative path resolution relative to base directory
- Fix symlink handling to prevent escape via symlinks
- Fix base directory constraint enforcement
- Implement additional checks for symlinks in path components
- Address TOCTOU (Time-of-Check-Time-of-Use) concerns

**Phase 3: Enhanced Testing (1-2h)**
- Fix all 4 failing tests
- Add additional test coverage for edge cases:
  - Symlink attacks that escape allowed directory
  - Relative path resolution within allowed base
  - Path traversal attempts (`../../../etc/passwd`)
  - Unicode normalisation attacks
  - Null byte injection attempts
- Ensure no regressions in passing tests

#### Success Criteria

- [ ] All 4 failing path validation tests pass
- [ ] No regressions in passing tests
- [ ] Enhanced test coverage for edge cases (100% coverage target)
- [ ] Security review confirms no bypasses possible
- [ ] Documentation updated with path validation security

## Security Considerations

### Input Validation

**Query Sanitization:**
- Maximum query length: 10,000 characters
- Strip control characters and excessive whitespace
- Detect and flag potential injection patterns
- Validate encoding (UTF-8)

**Injection Prevention:**
- No eval() or exec() of query content
- Pattern detection for SQL/NoSQL injection attempts
- Escape special characters in logging
- Sanitize before ML model input

**Rate Limiting:**
- Per-user classification rate limits
- Prevent classification DoS attacks
- Graceful degradation under load

## Migration Guide

### From v0.6.0

**No Breaking Changes** - This is a new feature addition.

**New Dependencies:**
- No new external dependencies
- Uses existing FastAPI framework
- Integrates with existing query pipeline

**Configuration Changes:**
- Add `query_classification` section to config.yml (see above)
- Optional: Configure model mapping for routing recommendations

**API Changes:**
- New endpoint: `POST /api/v1/classify` (optional, for testing)
- Query pipeline automatically uses classification if enabled
- No changes to existing query endpoints

### Opt-In Behaviour

Classification is **enabled by default** but query routing decisions remain manual until v0.6.2 (Automatic Model Routing) is implemented. In v0.6.1, classification provides:
- Query metadata logging for analysis
- Foundation for future routing features
- Manual routing hints (logged but not acted upon)

**To disable classification:**
```yaml
query_classification:
  enabled: false
```
