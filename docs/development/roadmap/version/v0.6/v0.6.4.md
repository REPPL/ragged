### OPTIMISE-005: Smart Caching Strategy (20-25 hours)

**Purpose:** Implement intelligent caching to reduce query latency and improve user experience.

#### Caching Strategies

**1. Frequency-Based Caching:**
- Cache queries that appear multiple times
- Track query frequency over sliding window
- Prioritise high-frequency queries for caching
- Cache eviction based on least-recently-used (LRU)

**2. Recency-Based Caching:**
- Cache recent queries (last 1-24 hours)
- Time-based TTL (time-to-live)
- Automatic expiration after TTL
- Refresh cache on re-query

**3. Predictive Caching:**
- Cache likely next queries based on patterns
- User session tracking (anonymised)
- Query sequence analysis
- Preload cache for common workflows

**4. Similarity-Based Caching:**
- Cache queries similar to current query
- Semantic similarity using embeddings
- Partial cache hits (similar queries)
- Cache result adaptation

#### Caching Layers

**1. Query Classification Cache:**
- Cache classification results (v0.6.1)
- TTL: 1 hour (classifications stable)
- Key: Query hash

**2. Model Routing Cache:**
- Cache routing decisions (v0.6.2)
- TTL: 1 hour
- Key: Classification hash

**3. Domain Detection Cache:**
- Cache domain detections (v0.6.3)
- TTL: 24 hours (document domains stable)
- Key: Document ID

**4. Retrieval Results Cache:**
- Cache retrieval results (embeddings, BM25, reranking)
- TTL: 30 minutes
- Key: Query hash + context scope

**5. LLM Response Cache:**
- Cache final LLM responses
- TTL: 15 minutes (responses can become stale)
- Key: Query hash + retrieval hash + model

#### Implementation Phases

**Phase 1: Caching Infrastructure (8-10h)**
- Cache backend (Redis or in-memory LRU)
- Cache key generation (consistent hashing)
- TTL management
- Cache eviction policies
- Cache size limits

## Security Considerations

### Input Validation

**Query Sanitization:**
- Validate queries before cache key generation
- Prevent cache key collision attacks
- Maximum query length enforcement
- Sanitise cache keys (no special characters)

**Cache Poisoning Prevention:**
- Validate cache entries before serving
- Hash-based cache keys (prevent guessing)
- No user-controlled cache keys
- Cache entry integrity validation

### Access Control

**Cache Access Restrictions:**
- Per-user cache isolation (if multi-user)
- No cross-user cache hits
- Cache access logging
- Sensitive data not cached without encryption

### Resource Limits

**Cache Size Limits:**
- Maximum cache size: 1GB (configurable)
- Per-cache-layer limits
- Automatic eviction when limit reached
- Disk space monitoring

**TTL Enforcement:**
- Strict TTL enforcement (prevent stale data)
- Maximum TTL: 24 hours
- Configurable TTL per cache layer
- TTL bypass prevention

### Rate Limiting

**Cache Operation Limits:**
- Maximum cache writes per second: 1000
- Maximum cache reads per second: 10000
- Per-user cache operation limits
- Prevent cache flooding attacks

### Security Testing

- [ ] Cache key collision tests
- [ ] Cache poisoning tests (malicious cache entries)
- [ ] TTL bypass tests
- [ ] Resource exhaustion tests (cache size limits)
- [ ] Rate limiting enforcement tests
- [ ] Cross-user cache isolation tests (if applicable)

## Configuration

### Analytics Settings

```yaml
# config.yml
analytics:
  enabled: true

  collection:
    query_metrics: true
    retrieval_quality: true
    model_performance: true
    cache_effectiveness: true
    gpu_utilisation: true
    memory_usage: true

  storage:
    database_path: "~/.ragged/analytics.db"
    max_database_size_mb: 500
    retention_days: 30
    cleanup_interval_hours: 24

  performance:
    collection_overhead_target_ms: 5
    async_writes: true
    batch_size: 100
```

### Caching Settings

```yaml
caching:
  enabled: true
  backend: "memory"  # Options: "memory", "redis"

  global:
    max_size_mb: 1024
    eviction_policy: "lru"  # Options: "lru", "lfu", "ttl"

  layers:
    query_classification:
      enabled: true
      ttl_seconds: 3600
      max_entries: 10000

    model_routing:
      enabled: true
      ttl_seconds: 3600
      max_entries: 10000

    domain_detection:
      enabled: true
      ttl_seconds: 86400  # 24 hours
      max_entries: 5000

    retrieval_results:
      enabled: true
      ttl_seconds: 1800   # 30 minutes
      max_entries: 1000

    llm_responses:
      enabled: true
      ttl_seconds: 900    # 15 minutes
      max_entries: 500

  strategies:
    frequency_based: true
    recency_based: true
    predictive: true
    similarity_based: false  # Experimental, disabled by default

  performance:
    cache_overhead_target_ms: 10
    warm_on_startup: true
    preload_popular_queries: true

  security:
    max_cache_operations_per_second: 1000
    per_user_isolation: false  # Enable for multi-user deployments
```

## Migration Guide

### From v0.6.3

**No Breaking Changes Before v1.0** - Breaking changes are acceptable in pre-1.0 versions. No migration compatibility layer required.

**New Dependencies:**
- SQLite (bundled with Python, for analytics)
- Optional: Redis (for distributed caching, not required for single-node)

**Configuration Changes:**
- Add `analytics` section to config.yml (optional, defaults shown above)
- Add `caching` section to config.yml (optional, defaults shown above)

**API Changes:**
- No changes to existing query endpoints
- Optional: New endpoints for analytics queries
  - `GET /api/v1/analytics/summary`
  - `GET /api/v1/analytics/cache`
  - `GET /api/v1/analytics/models`

### Behaviour Changes

**Automatic Analytics Collection (Enabled by Default):**
- Metrics automatically collected for all queries
- Analytics data stored in `~/.ragged/analytics.db`
- Minimal performance impact (<5ms per query)

**Automatic Caching (Enabled by Default):**
- Queries automatically cached after first execution
- Cache warms up over time
- Cache hit rate improves with usage

**To Disable Analytics:**
```yaml
analytics:
  enabled: false
```

**To Disable Caching:**
```yaml
caching:
  enabled: false
```
