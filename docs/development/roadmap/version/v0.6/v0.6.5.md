# v0.6.5: Streaming & Parallel Performance

**Focus:** Response streaming and parallel retrieval optimisation

**Hours:** 27-35 hours

**Dependencies:** v0.6.0-v0.6.4

**Status:** Planned

---

## Overview

Version 0.6.5 introduces streaming response generation and parallel retrieval processing to dramatically improve both perceived and actual performance. Streaming provides immediate feedback to users while parallel retrieval reduces actual latency by executing retrieval operations concurrently.

**What This Version Delivers:**
- OPTIMISE-005: Streaming Response Generation (12-15h)
- OPTIMISE-006: Parallel Retrieval Pipeline (15-20h)

**Why This Version is Critical:**
- Reduces perceived latency by 60-80% (streaming)
- Reduces actual retrieval latency by 33-60% (parallelisation)
- Improves user experience with immediate feedback
- Foundation for real-time multi-modal applications

### OPTIMISE-006: Parallel Retrieval Pipeline (15-20 hours)

**Purpose:** Execute retrieval operations concurrently to reduce actual query latency.

#### Performance Gains

**Sequential Pipeline (Current):**
```
Vector search:     200ms
BM25 search:       150ms
Reranking:         100ms
Total:             450ms
```

**Parallel Pipeline (Target):**
```
Vector + BM25:     max(200ms, 150ms) = 200ms
Reranking:         100ms
Total:             300ms
Reduction:         33% (150ms saved)
```

**With optimisations (v0.6.3 domain adaptation):**
- Parallel: 300ms → 180ms (40% reduction)
- Total improvement: 60% vs original sequential

#### Implementation Phases

**Phase 1: Concurrent Retrieval (6-8h)**
- asyncio integration for retrieval
- Parallel vector + BM25 searches
- Result synchronisation
- Thread-safe result merging

**Phase 2: Pipeline Optimisation (4-6h)**
- Batch processing optimisation
- Connection pooling
- Resource management
- Memory-efficient result handling

**Phase 3: Reranking Integration (3-4h)**
- Sequential reranking after parallel retrieval
- Result fusion strategies
- Score normalisation
- Quality validation

**Phase 4: Testing & Benchmarking (2-4h)**
- Latency benchmarks (sequential vs parallel)
- Accuracy validation (no regression)
- Concurrent load testing
- Resource usage profiling

#### Success Criteria

## Security Considerations

### Input Validation

**Query Sanitization:**
- Maximum query length: 10,000 characters
- Strip control characters and excessive whitespace
- Detect and flag potential injection patterns
- Validate encoding (UTF-8)

**Stream Security:**
- Sanitize tokens before streaming (prevent XSS in web UI)
- Escape control characters in CLI output
- Validate stream integrity
- Prevent information leakage in error streams

### Rate Limiting

**Streaming Protection:**
- Per-user streaming rate limits (prevent streaming DoS)
- Maximum concurrent streams per user
- Token generation rate limits
- Graceful degradation under load

**Parallel Retrieval Protection:**
- Maximum concurrent retrievals per user
- Resource pool limits (connections, threads)
- Query queue management
- Circuit breaker for overload protection

### Resource Management

**Memory Safety:**
- Stream buffer size limits
- Parallel retrieval result size limits
- Connection pool size limits
- Memory monitoring and alerts

**Concurrency Safety:**
- Thread-safe result merging
- Proper lock management
- Deadlock prevention
- Race condition testing

### Security Testing

- [ ] Streaming DoS attack tests (excessive concurrent streams)
- [ ] Injection attack tests (XSS in streamed tokens, SQL/NoSQL in queries)
- [ ] Malicious input handling (very long queries, control chars, Unicode exploits)
- [ ] Rate limiting enforcement tests
- [ ] Resource exhaustion tests (memory, connections, threads)
- [ ] Concurrent access race condition tests
- [ ] Stream interrupt/stop security validation

## Configuration

### Streaming Settings

```yaml
# config.yml
streaming:
  enabled: true
  time_to_first_token_target_ms: 1000

  rate_limits:
    max_concurrent_streams_per_user: 3
    token_generation_rate_limit: 1000  # tokens per minute

  buffers:
    stream_buffer_size_tokens: 100
    max_stream_duration_seconds: 300

  cli:
    progressive_output: true
    ansi_formatting: true

  web_ui:
    websocket_streaming: true
    update_interval_ms: 50
```

### Parallel Retrieval Settings

```yaml
query_processing:
  parallel_retrieval:
    enabled: true
    max_concurrent_retrievals_per_query: 2  # vector + BM25

  resource_limits:
    max_concurrent_queries_per_user: 5
    connection_pool_size: 20
    thread_pool_size: 10

  performance:
    retrieval_timeout_ms: 5000
    reranking_timeout_ms: 2000

  circuit_breaker:
    enabled: true
    failure_threshold: 5
    timeout_seconds: 30
```

## Migration Guide

### From v0.6.4

**No Breaking Changes** - Streaming and parallel retrieval are internal optimisations.

**New Configuration:**
- Add `streaming` section to config.yml (optional, defaults shown above)
- Add `parallel_retrieval` settings to `query_processing` (optional)

**Behaviour Changes:**
- CLI output now streams by default (can disable with `streaming.cli.progressive_output: false`)
- Web UI shows real-time generation (no UI changes required)
- Queries run faster due to parallel retrieval (no API changes)

**Opt-Out:**
```yaml
streaming:
  enabled: false

query_processing:
  parallel_retrieval:
    enabled: false
```

## Performance Impact

### Expected Metrics

**Streaming:**
- Time to first token: <1 second (p95)

**Parallel Retrieval:**

- Total query latency reduction: 20-40% (depending on retrieval proportion)
- CPU usage: +20-30% during retrieval (more parallelism)
- Memory usage: +50-100MB (concurrent operations)

**Combined Impact:**
- Perceived latency: 60-80% reduction (streaming)
- Actual latency: 20-40% reduction (parallel retrieval)
- User experience: Significantly improved
