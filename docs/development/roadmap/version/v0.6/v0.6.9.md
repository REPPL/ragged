## Security Considerations

### WebSocket Security

**Connection Security:**
- Use WSS (WebSocket Secure) over TLS in production
- Authenticate WebSocket connections with session tokens
- Validate origin headers to prevent CSRF attacks
- Implement connection rate limiting (max 10 connections per IP)

**Message Validation:**
- Sanitise all incoming WebSocket messages
- Validate message schema before processing
- Reject malformed or unexpected message types
- Implement message size limits (max 1MB per message)

**DoS Prevention:**
- Rate limit message frequency (max 100 messages/second per connection)
- Implement heartbeat/ping-pong to detect dead connections
- Auto-disconnect inactive connections (timeout: 5 minutes)
- Connection pool limits to prevent exhaustion

### D3.js XSS Prevention

**Data Sanitization:**
- Sanitise all node labels and properties before rendering
- Use D3's text() method instead of html() for user-generated content
- Escape HTML entities in graph metadata
- Validate SVG attributes to prevent script injection

**Graph Security:**
- Limit maximum nodes and edges (prevent rendering DoS)
- Sanitise graph data from API before D3 rendering
- No eval() or Function() constructor with graph data
- Content Security Policy blocks inline SVG scripts

**User Input in Graphs:**
- Escape all document names, entity labels, topic titles
- Validate colours and styling properties (whitelist approach)
- No user-controlled URLs in graph links
- Filter control characters from filter inputs

### Real-Time Data Sanitisation

**GPU Metrics:**
- Validate numeric ranges (GPU usage: 0-100%, memory: positive integers)
- Reject non-numeric or malformed metrics
- Rate limit metrics updates (max 1 update/second)
- No user-controlled metric labels

**Performance Data:**
- Sanitise query descriptions in performance logs
- Validate latency values (positive numbers, reasonable max: 60000ms)
- Escape all user-generated content in charts
- No sensitive data in performance visualisations (hash queries)

**Chart Rendering:**
- Use trusted charting libraries only (D3.js, Chart.js)
- Sanitise all chart labels and tooltips
- Validate data arrays for expected structure
- Prevent script execution in chart event handlers

## Configuration

### WebSocket Settings

```typescript
// src/lib/config/websocket.ts
export const websocketConfig = {
  url: process.env.VITE_WS_URL || 'wss://localhost:8000/ws',

  connection: {
    reconnectInterval: 5000, // 5 seconds
    maxReconnectAttempts: 10,
    connectionTimeout: 10000, // 10 seconds
    heartbeatInterval: 30000 // 30 seconds
  },

  security: {
    validateOrigin: true,
    requireAuth: true,
    maxMessageSize: 1048576, // 1MB
    rateLimit: {
      messagesPerSecond: 100,
      maxConnections: 10
    }
  },

  monitoring: {
    metricsUpdateInterval: 1000, // 1 second
    historyLength: 300 // 5 minutes at 1s intervals
  }
}
```


## Migration Guide

### From v0.6.8

**No Breaking Changes Before v1.0** - Breaking changes are acceptable in pre-1.0 versions. No migration compatibility layer required.

**New Features:** Advanced visualisations, WebSocket real-time updates, enhanced document preview.

**What Changes:**
- WebSocket support added for real-time monitoring
- D3.js integration for knowledge graph
- Enhanced PDF preview with highlighting
- GPU monitoring dashboard

**Migration Steps:**
1. Install new npm dependencies: `npm install d3 @types/d3 ws @types/ws`
2. Configure WebSocket URL in `.env.local` (see Configuration section)
3. Enable GPU monitoring in `config.yml` (optional)
4. No API changes - backwards compatible with v0.6.8

**Configuration Changes:**
```bash
# .env.local
VITE_WS_URL=wss://localhost:8000/ws  # Add WebSocket URL
```

**Data Compatibility:**
- No changes to backend data storage
- Existing documents and queries work with new visualisations
- Graph data generated on-demand from existing metadata

## Performance Impact

### Expected Metrics

**Initial Load:**
- D3.js bundle adds ~200KB gzipped
- WebSocket library adds ~50KB gzipped
- Total bundle size increase: ~250KB
- Initial load impact: +500ms (one-time)

**Runtime Performance:**
- Graph rendering: <1s for 500 nodes, <3s for 1000 nodes
- WebSocket overhead: <10ms per message
- Real-time chart updates: <100ms latency
- Memory usage: +50-150MB (depends on graph size)

**Network:**
- WebSocket connection: Persistent, low overhead
- Metrics updates: ~1KB per update (compressed)
- Graph data: ~10-50KB depending on complexity
- PDF preview: Rendered client-side (no additional network)

**Resource Usage:**
- CPU: +5-15% during graph interactions
- GPU: Minimal (canvas-based rendering)
- RAM: +50-150MB (graph caching, chart history)
- Disk: No additional storage
