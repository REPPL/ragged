## Overview

Version 0.6.2 implements automatic model routing based on query characteristics from v0.6.1's classification system. Different model sizes and specialisations are selected to optimise latency for simple queries while maintaining quality for complex ones.

**Additionally, v0.6.2 implements MEDIUM-priority security enhancements from the v0.6.0 audit, including Redis-backed session persistence, session monitoring metrics, and plugin sandbox enforcement verification.**

**What This Version Delivers:**

## Features

### OPTIMISE-002: Automatic Model Routing (30-40 hours)

**Purpose:** Automatically select the optimal model based on query classification metadata from v0.6.1.

#### Routing Strategy

**Model Selection Logic:**

**1. Simple Factual Queries (Complexity 1-2):**
- **Model:** `llama3.2:3b` (fast)
- **Rationale:** Simple lookups don't require large models
- **Expected latency:** 200-400ms
- **Accuracy target:** 90%+

**2. Medium Conceptual Queries (Complexity 3-5):**
- **Model:** `llama3.2:8b` (balanced)
- **Rationale:** Explanations need moderate reasoning
- **Expected latency:** 600-1000ms
- **Accuracy target:** 93%+

**3. Complex Analytical Queries (Complexity 6-8):**
- **Model:** `llama3.2:70b` (quality)
- **Rationale:** Deep analysis requires full model capacity
- **Expected latency:** 2000-3000ms
- **Accuracy target:** 95%+

**4. Very Complex Multi-hop Queries (Complexity 9-10):**
- **Model:** `llama3.2:70b` (quality)
- **Rationale:** Multi-hop reasoning demands best model
- **Expected latency:** 3000-5000ms
- **Accuracy target:** 96%+

**5. Vision/Multi-modal Queries:**
- **Model:** `llava` or `llama3.2-vision:90b`
- **Rationale:** Requires vision capabilities
- **Expected latency:** 2500-4000ms
- **Accuracy target:** 92%+

**6. Creative/Open-ended Queries:**
- **Model:** `mistral:latest` (balanced creativity)
- **Rationale:** Creative generation benefits from diverse model
- **Expected latency:** 800-1200ms
- **Accuracy target:** 90%+

#### API Design

```python
from src.optimisation import QueryClassifier, ModelRouter

# Initialise components
classifier = QueryClassifier()
router = ModelRouter()

# Classify and route
query = "How does ColPali compare to traditional OCR for document understanding?"
classification = classifier.classify(query)

# Automatic routing
selected_model = router.select_model(classification)
print(selected_model.name)              # "llama3.2:70b"
print(selected_model.estimated_latency) # 2500 (ms)
print(selected_model.rationale)         # "Complex comparison query requires quality model"

# Execute query with routed model
from src.models import OllamaClient
client = OllamaClient(model=selected_model.name)
response = client.generate(query, context=retrieval_results)
```

### SECURITY-003: Session Persistence with Redis Backend (8-16 hours) ⚠️ MEDIUM PRIORITY

**Purpose:** Implement Redis-backed session storage for production scalability and persistence across restarts.

**Audit Reference:** [v0.6.0 Security Audit](../../../../audit/security/baseline/v0.6.0-security-audit.md) Section 3.2 H-2, CR-SEC-003

#### Problem Statement

Sessions currently stored in-memory (`SessionSecurityMiddleware`). This causes:
1. Session loss on restart (users must re-authenticate)
2. No horizontal scaling (can't run multiple API instances with shared sessions)
3. Memory exhaustion risk (unbounded session storage in production)

#### Implementation Phases

**Phase 1: Session Store Architecture (3-5h)**
- Create `SessionStore` abstract interface
- Implement `InMemorySessionStore` (existing behaviour)
- Implement `RedisSessionStore` for production
- Graceful fallback to in-memory if Redis unavailable

**Phase 2: Middleware Integration (3-5h)**
- Update `SessionSecurityMiddleware` to use SessionStore
- Redis connection pooling
- TTL-based automatic expiry in Redis
- Session data serialisation/deserialisation

**Phase 3: Docker & Configuration (2-4h)**
- Add Redis service to docker-compose.yml
- Redis persistence configuration
- Environment variable configuration (`REDIS_URL`)
- Health checks and monitoring

**Phase 4: Testing (2-4h)**
- Unit tests for both session stores
- Integration tests with Redis container
- Session persistence verification across restarts
- Concurrent session handling tests
- Failover tests (Redis unavailable → in-memory fallback)

#### Success Criteria

- [ ] SessionStore interface implemented with two backends
- [ ] In-memory store (development default)
- [ ] Redis store (production option)
- [ ] Graceful fallback functional
- [ ] Redis service added to docker-compose.yml
- [ ] Sessions persist across service restarts
- [ ] 100% test coverage for session stores
- [ ] Integration tests pass with Redis
- [ ] Documentation for production deployment

#### Files Changed

- `src/web/session/store.py` - SessionStore interface + implementations
- `src/web/middleware/security.py` - Updated SessionSecurityMiddleware
- `docker-compose.yml` - Redis service

### SECURITY-005: Plugin Sandbox Enforcement Verification (4-8 hours) ⚠️ MEDIUM PRIORITY

**Purpose:** Create comprehensive test plugins to verify sandbox resource limits are actually enforced.

**Audit Reference:** [v0.6.0 Security Audit](../../../../audit/security/baseline/v0.6.0-security-audit.md) Section 3.3 M-3, CR-SEC-005

#### Problem Statement

Plugin sandbox implements resource limits (`setrlimit`) and permission checks, but actual enforcement has not been verified with real test plugins. Missing verification:
1. Memory limits actually enforced?
2. CPU limits trigger SIGXCPU?
3. Network isolation works on Linux?
4. Process limits prevent fork bombs?
5. File system restrictions effective?

#### Implementation Phases

**Phase 1: Test Plugin Creation (2-3h)**
- Create `memory_hog.py` (attempts to exceed memory limit)
- Create `cpu_burner.py` (attempts to exceed CPU limit)
- Create `network_accessor.py` (attempts network access)
- Create `fork_bomb.py` (attempts to spawn many processes)
- Create `file_accessor.py` (attempts filesystem access outside allowed paths)

**Phase 2: Enforcement Test Suite (2-3h)**
- Test memory limit enforcement (`test_memory_limit_enforced`)
- Test CPU limit enforcement (`test_cpu_limit_enforced`)
- Test network isolation enforcement (`test_network_isolation_enforced` - Linux only)
- Test process limit enforcement (`test_fork_bomb_prevented`)
- Test filesystem restriction enforcement

**Phase 3: CI Integration (1-2h)**
- Add tests to CI/CD pipeline
- Platform-specific test skipping (network isolation Linux-only)
- Documentation of sandbox capabilities/limitations per platform

#### Success Criteria

- [ ] Test plugins created for each resource limit

## Security Considerations

### Input Validation

**Query Sanitization:**
- Validate classification metadata before routing
- Maximum query length enforcement (inherited from v0.6.1)
- Prevent routing manipulation via malicious metadata
- Sanitise model names (prevent command injection)

**Model Selection Validation:**
- Whitelist of allowed models
- Reject invalid model names
- Validate model availability before routing
- Prevent arbitrary model execution

### Access Control

**Model Access Restrictions:**
- Per-user model access policies
- Rate limiting per model tier
- Quota management (GPU/CPU resources)
- Audit logging of model usage

**Resource Limits:**
- Maximum concurrent model requests per user
- GPU memory allocation limits
- Request queue size limits
- Timeout enforcement per model

### Rate Limiting

**Per-Model Rate Limits:**
- 3b model: 100 requests/minute per user
- 8b model: 50 requests/minute per user
- 70b model: 20 requests/minute per user
- Vision models: 30 requests/minute per user

**Global Rate Limits:**
- Total GPU requests: 200/minute across all users
- Model switching frequency limit: 10/minute per user
- Prevent routing DoS attacks

### Security Testing

- [ ] Model name injection tests (prevent command execution)
- [ ] Routing manipulation tests (malicious classification metadata)
- [ ] Rate limiting enforcement tests (per-model and global)
- [ ] Resource exhaustion tests (GPU memory, concurrent requests)
- [ ] Access control validation (unauthorised model access)
- [ ] Fallback security (model unavailable doesn't leak info)

## Migration Guide

### From v0.6.1

**No Breaking Changes Before v1.0** - Breaking changes are acceptable in pre-1.0 versions. No migration compatibility layer required.

**New Dependencies:**
- Requires v0.6.1 (Query Classification) to be enabled
- Uses existing Ollama API (no new external dependencies)

**Configuration Changes:**
- Add `model_routing` section to config.yml (see above)
- Configure model availability per environment
- Set rate limits based on hardware capacity

**API Changes:**
- No changes to existing query endpoints
- Query pipeline automatically uses routing if enabled
- Optional: New endpoint `POST /api/v1/routing/preview` for testing

### Behaviour Changes

**Automatic Routing (Enabled by Default):**
- Queries now automatically routed to appropriate models
- Simple queries use faster models (reduced latency)
- Complex queries use quality models (maintained accuracy)
- Routing decisions logged for analytics

**To Disable Routing:**
```yaml
model_routing:
  enabled: false
  default_model: "llama3.2:8b"  # All queries use this model
```

**Manual Model Override:**
```python
# API request with manual model selection
POST /api/v1/query
{
  "query": "What is RAG?",
  "model": "llama3.2:70b",  # Override automatic routing
  "bypass_routing": true
}
```
