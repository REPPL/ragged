## Overview

Version 0.6.11 transforms the internal FastAPI (v0.6.7) into a public developer API with versioning, API key management, client SDKs, and external documentation.

**What This Version Delivers:**
- API versioning (`/v1/...`)
- API key management and authentication
- Rate limiting with tiered quotas
- Client SDKs (Python, JavaScript/TypeScript)
- Developer documentation portal

**Why After UI:**
- API proven stable through internal use (v0.6.8-v0.6.10)
- Allows time for API design refinement
- Svelte UI validates API completeness

- **Versioning:** `/v1/...` prefix (allows future `/v2/...`)
- **Authentication:** API key generation and rotation
- **Rate Limiting:** Per-key quotas (free, developer, enterprise tiers)


## Security Considerations

### API Key Management

**Key Generation:**
- Cryptographically secure random key generation (256-bit minimum)
- Key prefix format: `rg_` followed by 32 characters
- Hash keys with bcrypt before storage (never store plaintext)
- Implement key rotation mechanism (max age: 90 days)
- Generate separate keys for development/production

**Key Storage:**
- Store hashed keys only in database
- Encrypt keys in transit (HTTPS only)
- No keys in logs or error messages
- Implement key revocation API endpoint
- Audit log for key usage and rotation

**Key Validation:**
- Rate limit key validation attempts (10 failures/minute → temporary ban)
- Validate key format before database lookup
- Timing-safe comparison to prevent timing attacks
- No key validation over HTTP (HTTPS only)
- Implement key scope validation (read/write/admin permissions)

### Rate Limiting

**Tiered Rate Limits:**
- Free tier: 1,000 requests/month, 10 requests/minute
- Developer tier: 50,000 requests/month, 100 requests/minute
- Enterprise tier: Unlimited requests, 1,000 requests/minute
- Different limits for expensive operations (document upload, embedding generation)

**Rate Limit Enforcement:**
- Use Redis for distributed rate limiting
- Sliding window algorithm (not fixed window)
- Return clear error messages with retry-after headers
- Implement burst allowance for spike traffic
- No rate limit bypass for any tier (including enterprise)

**DoS Prevention:**
- IP-based rate limiting as secondary measure
- Request size limits (body: 50MB, query params: 4KB)
- Timeout limits per endpoint (30s query, 5min upload)
- Concurrent request limits per API key (max: 10)
- Implement exponential backoff recommendations in SDK

### SDK Security

**Client-Side Security:**
- Never log API keys in SDK
- Warn users not to commit keys to version control
- Provide environment variable configuration examples
- Validate API key format before sending requests
- Implement automatic retry with exponential backoff

**SDK Integrity:**
- Sign SDK releases with GPG
- Publish checksums for npm/pip packages
- Use npm/pip package verification
- Regular dependency updates and vulnerability scanning
- Minimal dependencies (reduce supply chain risk)

**Error Handling:**
- No sensitive data in error messages
- Generic errors for authentication failures (no key format hints)
- No stack traces in production
- Rate limit error details sanitised

### API Versioning Security

**Version Isolation:**
- Separate security policies per API version
- No automatic migration of authentication between versions
- Version-specific rate limits
- Deprecation warnings in headers (no breaking redirects)

**Backwards Compatibility:**
- Security fixes backported to supported versions (v1, v2)
- Breaking security changes require major version bump
- Transparent migration path for deprecated versions
- No silent security downgrades

**Sunset Policy:**
- 12-month minimum support for each API version
- 6-month deprecation warning period
- Clear migration documentation
- No forced upgrades (opt-in migrations only)

### OAuth Integration (Future)

**OAuth 2.0 Preparation:**
- Design API with OAuth scopes in mind
- Implement scope-based access control foundation
- Token refresh mechanism architecture
- Prepare for multiple authentication methods

**Security Considerations:**
- PKCE flow for public clients
- State parameter for CSRF protection
- Token expiration and refresh
- Scope validation on every request

## Configuration

### API Key Settings

```yaml
# config.yml
api:
  versioning:
    enabled: true
    default_version: "v1"
    supported_versions: ["v1"]
    deprecation_warning_months: 6

  authentication:
    key_prefix: "rg_"
    key_length: 32
    hash_algorithm: "bcrypt"
    hash_rounds: 12
    key_rotation_days: 90
    require_https: true

  rate_limiting:
    enabled: true
    backend: "redis"
    redis_url: "redis://localhost:6379"

    tiers:
      free:
        requests_per_month: 1000
        requests_per_minute: 10
        burst_allowance: 20
        concurrent_requests: 2

      developer:
        requests_per_month: 50000
        requests_per_minute: 100
        burst_allowance: 150
        concurrent_requests: 5

      enterprise:
        requests_per_month: -1  # Unlimited
        requests_per_minute: 1000
        burst_allowance: 1500
        concurrent_requests: 10

  security:
    max_request_size_mb: 50
    max_query_param_size_kb: 4
    request_timeout_seconds: 30
    upload_timeout_seconds: 300
    validation_attempts_per_minute: 10
```

## Migration Guide

### From v0.6.10

**No Breaking Changes Before v1.0** - Breaking changes are acceptable in pre-1.0 versions. No migration compatibility layer required.

**New Features:** Public API with versioning, API key authentication, client SDKs, developer portal.

**What Changes:**
- API accessible externally with API keys
- Versioned endpoints: `/v1/...`
- Rate limiting enforced per tier
- Client SDKs available for Python and JavaScript

**Migration Steps:**
1. Generate API key via developer portal or CLI
2. Update API endpoint to `/v1/` prefix
3. Add API key to headers: `Authorization: Bearer rg_...`
4. Install SDK: `pip install ragged-client` or `npm install @ragged/client`
5. No changes to existing internal API usage (backwards compatible)

**Configuration Changes:**
```yaml
# config.yml
api:
  versioning:
    enabled: true
    default_version: "v1"
  rate_limiting:
    enabled: true
```

**Environment Variables:**
```bash
# .env
RAGGED_API_KEY=rg_your_key_here
REDIS_URL=redis://localhost:6379  # For rate limiting
```

**Data Compatibility:**
- No changes to backend data storage
- Existing queries and documents accessible via new API
- API keys stored in new `api_keys` table

## Usage Examples

### Python SDK

```python
from ragged_client import RaggedClient

# Initialise client
client = RaggedClient(api_key="rg_your_key_here")

# Text query
results = client.query.text("neural architecture search")

# Image query
results = client.query.image("path/to/image.png")

# Hybrid query
results = client.query.hybrid(
    text="neural architecture",
    image="path/to/image.png",
    text_weight=0.7,
    image_weight=0.3
)

# Upload document
client.documents.upload("path/to/paper.pdf")

# List documents
documents = client.documents.list()
```

### JavaScript SDK

```typescript
import { RaggedClient } from '@ragged/client';

// Initialise client
const client = new RaggedClient({ apiKey: 'rg_your_key_here' });

// Text query
const results = await client.query.text('neural architecture search');

// Image query
const imageResults = await client.query.image('./image.png');

// Hybrid query
const hybridResults = await client.query.hybrid({
  text: 'neural architecture',
  image: './image.png',
  textWeight: 0.7,
  imageWeight: 0.3
});

// Upload document
await client.documents.upload('./paper.pdf');

// List documents
const documents = await client.documents.list();
```

### API Key Management

```bash
# Generate new API key (CLI)
ragged api-key create --name "Production Key" --tier developer

# List API keys
ragged api-key list

# Revoke API key
ragged api-key revoke rg_abc123...

# Rotate API key
ragged api-key rotate rg_abc123...

# View usage statistics
ragged api-key usage rg_abc123... --days 30
```
