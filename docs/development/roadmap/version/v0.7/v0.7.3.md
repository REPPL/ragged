# Ragged v0.7.3 Roadmap - Embedded ChromaDB Option (Optional)

**Status:** Conditional (implement only if Docker is major pain point)

**Total Hours:** 18-28 hours (AI implementation)

**Focus:** Docker-free installation option with embedded database

**Breaking Changes:** None

**Dependencies:** Requires v0.7.1 completion and Docker pain point validation

**Purpose:** Eliminate Docker dependency for simplified deployment

---

## Overview

Version 0.7.3 provides an embedded ChromaDB mode that eliminates the Docker requirement, offering a single-process deployment option for users who cannot or prefer not to use Docker. Whilst Docker provides excellent isolation and performance, it can be challenging in environments with restrictions (corporate policies, edge devices, air-gapped systems).

**Rationale:** Removing the Docker dependency makes ragged accessible to users in constrained environments whilst maintaining functional parity with Docker-based deployment.

**Trade-off:** Embedded mode may be 10-20% slower than Docker-based ChromaDB but removes complexity and resource overhead of Docker.

## EMBED-001: Embedded ChromaDB Mode (12-18 hours)

**Problem:** Docker is not available or permitted in some deployment environments.

**Implementation:**

1. **Research embedded ChromaDB integration** [2-3 hours]
   - Review ChromaDB Python client embedded mode
   - Evaluate alternatives:
     - **chromadb.Client()** - In-memory, ephemeral (not suitable)
     - **chromadb.PersistentClient()** - File-based, persistent (recommended)
     - **chromadb.HttpClient()** - Docker-based (current approach)
   - Test ChromaDB embedded mode:
     - Performance benchmarks (query latency, ingestion speed)
     - Memory usage comparison (embedded vs Docker)
     - File size growth patterns
     - Concurrency handling
   - Identify limitations:
     - Single process (no horizontal scaling)
     - No built-in backup/restore (need custom implementation)
     - SQLite backend (vs DuckDB in Docker)

2. **Implement database mode detection** [2-3 hours]
   - Auto-detect available database modes:
     ```python
     def detect_database_mode() -> DatabaseMode:
         """Detect which database mode to use."""
         if docker_available() and user_preference != "embedded":
             return DatabaseMode.DOCKER
         elif chromadb_installed():
             return DatabaseMode.EMBEDDED
         else:
             raise DatabaseNotAvailableError()
     ```
   - Priority order:
     1. User preference (`.env`: `RAGGED_DATABASE_MODE=docker|embedded`)
     2. Docker availability (check if Docker daemon running)
     3. Fallback to embedded if Docker unavailable
   - Create abstraction layer:
     ```python
     class DatabaseClient:
         """Abstract database client (Docker or embedded)."""
         def __init__(self, mode: DatabaseMode):
             if mode == DatabaseMode.DOCKER:
                 self.client = chromadb.HttpClient(...)
             else:
                 self.client = chromadb.PersistentClient(path="~/.ragged/chromadb")

         def get_or_create_collection(self, name: str) -> Collection:
             return self.client.get_or_create_collection(name)

         # Uniform interface regardless of mode
     ```

3. **Implement file-based persistence** [2-3 hours]
   - Configure ChromaDB persistent storage:
     - Data directory: `~/.ragged/chromadb/`
     - Settings file: `~/.ragged/chromadb/chroma.sqlite3`
     - Collection data: `~/.ragged/chromadb/collections/`
   - Handle file permissions:
     - Create directories with correct permissions
     - Handle multi-user scenarios (file locking)
   - Add database initialization:
     - First-run setup creates directory structure
     - Health check validates database accessibility
     - Repair corrupted databases (re-index if needed)

4. **Add migration path between modes** [2-3 hours]
   - Implement `ragged database migrate --from docker --to embedded`:
     - Export collections from Docker ChromaDB
     - Import into embedded ChromaDB
     - Validate data integrity (count, sample queries)
   - Implement `ragged database migrate --from embedded --to docker`:
     - Reverse migration path
     - Start Docker ChromaDB if not running
     - Import data
   - Add `ragged database export --format backup`:
     - Export to portable format (JSON/SQLite)
     - Include metadata, embeddings, documents
   - Add `ragged database import --from backup.json`:
     - Import into current mode
     - Validate and report

5. **Update installation process** [2-3 hours]
   - Modify installation wizard (INSTALL-005 from v0.7.0):
     - Ask: "Use Docker for ChromaDB? [Y/n] (Recommended for performance)"
     - If no Docker: "Use embedded database? [Y/n] (Single-process, no Docker required)"
   - Install embedded ChromaDB Python package:
     - Add to `pyproject.toml`: `chromadb>=0.4.0` (with embedded extras)
   - Skip Docker setup if embedded mode chosen:
     - Don't start `docker compose up chromadb`
     - Don't check Docker availability
   - Update health check (INSTALL-006 from v0.7.0):
     - Show database mode: "Database: Embedded (file-based)"
     - Show storage location: "Storage: ~/.ragged/chromadb/ (2.3GB)"

6. **Add configuration management** [1-1.5 hours]
   - Environment variable: `RAGGED_DATABASE_MODE=docker|embedded|auto`
   - CLI command: `ragged database mode set embedded`
   - CLI command: `ragged database mode status`
   - Configuration preset for embedded mode:
     - `templates/config-embedded.env` (optimised for embedded)

**Files:**
- `src/database/embedded.py` (new - embedded ChromaDB client)
- `src/database/client.py` (modify - add mode detection and abstraction)
- `src/database/migration.py` (new - migrate between modes)
- `src/commands/database.py` (new - database management commands)
- `src/config/settings.py` (modify - add DATABASE_MODE setting)
- `scripts/install.sh` (modify - add embedded mode option)
- `templates/config-embedded.env` (new - embedded mode preset)

**⚠️ MANUAL TEST:**
- Install with embedded mode on system without Docker
- Ingest documents, run queries (verify functional parity)
- Migrate from Docker to embedded and back
- Test performance (compare to Docker)
- Check storage growth patterns

**Success Criteria:**
- Embedded mode achieves 80-90% of Docker performance
- Installation without Docker completes in <8 minutes

## EMBED-002: Embedded Mode Optimisations (6-10 hours)

**Problem:** Embedded ChromaDB may have performance gaps compared to Docker-based deployment.

**Implementation:**

1. **Profile embedded mode performance** [1.5-2 hours]
   - Benchmark embedded vs Docker:
     - Query latency (p50, p95, p99)
     - Ingestion speed (documents/sec)
     - Memory usage (resident set size)
     - Storage efficiency (bytes/document)
   - Identify bottlenecks:
     - SQLite performance (embedded backend)
     - Python overhead (in-process vs HTTP)
     - Memory management (garbage collection)
   - Document performance characteristics:
     - When embedded is acceptable (small datasets, <100k docs)
     - When Docker is required (large datasets, high concurrency)

2. **Optimise query performance** [2-3 hours]
   - SQLite optimisations:
     - Enable WAL mode: `PRAGMA journal_mode=WAL`
     - Increase cache size: `PRAGMA cache_size=-64000` (64MB)
     - Optimise page size: `PRAGMA page_size=4096`
   - Connection pooling:
     - Reuse ChromaDB client connections
     - Implement connection warming (pre-connect)
   - Query caching:
     - Cache frequent queries (LRU cache)
     - Invalidate cache on data changes
   - Batch processing:
     - Batch similar queries together
     - Reduce overhead of multiple client calls

3. **Optimise memory management** [2-3 hours]
   - Configure ChromaDB memory limits:
     - Set max memory usage (prevent OOM)
     - Implement memory pressure detection
   - Implement lazy loading:
     - Load collections on demand
     - Unload unused collections
   - Garbage collection tuning:
     - Adjust GC thresholds for ChromaDB workload
     - Force GC after large operations (ingestion)
   - Monitor memory usage:
     - Add `ragged database memory-usage` command
     - Show memory breakdown (collections, cache, overhead)

4. **Add backup and restore** [1.5-2 hours]
   - Implement `ragged database backup`:
     - Copy `~/.ragged/chromadb/` to backup location
     - Create compressed archive (`.tar.gz`)
     - Include metadata (version, date, size)
   - Implement `ragged database restore --from backup.tar.gz`:
     - Stop ragged services
     - Extract backup to temporary location
     - Validate backup integrity
     - Replace current database
     - Restart services
   - Add automatic backups:
     - Before major operations (upgrade, migration)
     - Scheduled backups (daily, weekly)
   - Add `ragged database backups list`
   - Add `ragged database backups cleanup --keep 5` (retain N backups)

5. **Create performance tuning guide** [0.5-1 hour]
   - Document `docs/guides/embedded-mode.md`:
     - When to use embedded vs Docker
     - Performance expectations
     - Tuning SQLite for ragged workload
     - Memory management tips
     - Backup/restore procedures
     - Troubleshooting common issues
   - Add performance comparison table:
     ```markdown
     | Metric | Docker | Embedded | Difference |
     |--------|--------|----------|------------|
     | Query latency (p95) | 120ms | 140ms | +17% |
     | Ingestion speed | 50 docs/sec | 42 docs/sec | -16% |
     | Memory usage | 1.2GB | 0.8GB | -33% |
     | Storage efficiency | 95% | 92% | -3% |
     ```
   - Provide recommendations:
     - Embedded: <100k documents, single user, edge devices
     - Docker: >100k documents, multi-user, production

**Files:**
- `src/database/embedded.py` (modify - add optimisations)
- `src/database/backup.py` (new - backup and restore)
- `src/commands/database.py` (modify - add backup commands)
- `docs/guides/embedded-mode.md` (new - tuning guide)

**⚠️ MANUAL TEST:**
- Run performance benchmarks (Docker vs embedded)

- Verify memory usage stays within limits

**Success Criteria:**

## Known Risks

- **Performance gap:** Embedded may be significantly slower for large datasets (>100k documents)
- **Concurrency limitations:** SQLite has limited concurrent write support
- **Horizontal scaling:** Embedded mode cannot scale across multiple machines
- **Maintenance burden:** Two database modes = two code paths to maintain
- **Migration complexity:** Moving data between modes may fail for large datasets
- **File corruption:** SQLite corruption risk higher than Docker (no isolation)

## Implementation Notes

### Performance Validation

Before implementing v0.7.3, build a **proof-of-concept (2-4 hours):**

```python
# poc_embedded.py - Test embedded ChromaDB performance
import chromadb
import time

# Test embedded mode
client = chromadb.PersistentClient(path="./test-db")
collection = client.get_or_create_collection("test")

# Benchmark ingestion
start = time.time()
for i in range(10000):
    collection.add(
        ids=[f"doc-{i}"],
        documents=[f"Test document {i}"],
        metadatas=[{"source": "test"}]
    )
print(f"Ingested 10k documents in {time.time() - start:.2f}s")

# Benchmark queries
start = time.time()
for i in range(100):
    results = collection.query(
        query_texts=["test query"],
        n_results=5
    )
print(f"100 queries in {time.time() - start:.2f}s")
```

**Decision:** Only implement v0.7.3 if PoC shows acceptable performance (ingestion >30 docs/sec, queries <200ms p95).

### Alternative: Defer to v0.8 or v0.9

If Docker pain points are minimal or embedded performance is inadequate, **defer embedded mode**:
- v0.8: Focus on advanced features (agents, knowledge graphs)
- v0.9: Revisit embedded mode as production deployment option

**Advantage:** Focus resources on higher-impact features, avoid premature optimisation.
