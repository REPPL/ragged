# Ragged v0.7.4 Roadmap - Testing & Quality Assurance (Conditional)

**Status:** Conditional (implement only if v0.7.3 is built)

**Total Hours:** 12-18 hours (AI implementation)

**Focus:** Quality gate for complete v0.7.x series

**Breaking Changes:** None

**Dependencies:** Only implement if v0.7.3 exists

**Purpose:** Comprehensive quality assurance before v0.8

---

## Overview

Version 0.7.4 serves as a quality gate for the extended v0.7.x series, providing comprehensive testing and documentation validation across all installation paths. This version is only needed if v0.7.3 (Embedded ChromaDB) is implemented, as it validates the additional complexity of supporting two database modes.

**Rationale:** If v0.7.3 adds embedded mode, we now have:
- 2 database modes (Docker, embedded)
- 4 installation methods (script, DMG, MSI, DEB/RPM - if v0.7.2 built)
- 8+ test combinations (platforms × modes × methods)

v0.7.4 ensures all combinations work reliably before moving to v0.8's advanced features.

---

## Decision Criteria

### Implement v0.7.4 if:

**Automatic decision:**
- ✓ v0.7.3 was implemented (embedded mode exists)
- **Rationale:** Two database modes require comprehensive validation

### Skip v0.7.4 if:

**Automatic decision:**
- ✗ v0.7.3 was skipped (only Docker mode exists)
- **Rationale:** Testing already comprehensive in v0.7.0-v0.7.2, no additional QA version needed

### Decision Point

**When:** Immediately after v0.7.3 completion (or decision to skip v0.7.3)

**How:** If `v0.7.3/` exists in roadmap and was implemented, then implement v0.7.4

## QA-001: Automated Installation Testing (5-7 hours)

**Problem:** Multiple installation paths (script, DMG, MSI, DEB, RPM) and modes (Docker, embedded) require systematic validation.

**Implementation:**

1. **Design CI/CD test matrix** [1-1.5 hours]
   - Define test matrix:
     ```yaml
     matrix:
       os: [macos-12, macos-13, macos-14, ubuntu-20.04, ubuntu-22.04, ubuntu-24.04, windows-2019, windows-2022]
       install_method: [script, native] # DMG/MSI/DEB/RPM depending on OS
       database_mode: [docker, embedded]
       include:
         - os: macos-13
           arch: arm64 # Apple Silicon
       exclude:
         - os: windows-*
           database_mode: embedded # Windows embedded not supported (if true)
     ```
   - Define test stages:
     1. Prerequisites check
     2. Installation
     3. Health check
     4. Document ingestion
     5. Query execution
     6. Uninstallation (verify cleanup)

2. **Implement GitHub Actions workflows** [2-3 hours]
   - Create `.github/workflows/installation-tests.yml`:
     ```yaml
     name: Installation Tests

     on:
       push:
         branches: [main, develop]
       pull_request:
         branches: [main]
       schedule:
         - cron: '0 2 * * *' # Daily at 2 AM UTC

     jobs:
       test-installation:
         runs-on: ${{ matrix.os }}
         strategy:
           matrix:
             ... # As defined above
         steps:
           - name: Checkout
             uses: actions/checkout@v3

           - name: Run installation
             run: ./scripts/install.sh --ci --database-mode ${{ matrix.database_mode }}

           - name: Verify health
             run: ragged health --json

           - name: Ingest test document
             run: ragged ingest pdf tests/fixtures/sample.pdf

           - name: Run test query
             run: ragged query "What is the main topic?"

           - name: Verify uninstall
             run: ./scripts/uninstall.sh --verify-cleanup
     ```
   - Add badges to README: ![Installation Tests](https://github.com/REPPL/ragged/workflows/Installation%20Tests/badge.svg)

3. **Implement VM-based testing** [1.5-2 hours]
   - Use **Vagrant** for clean VM testing:
     ```ruby
     # Vagrantfile
     Vagrant.configure("2") do |config|
       config.vm.define "ubuntu" do |ubuntu|
         ubuntu.vm.box = "ubuntu/jammy64"
         ubuntu.vm.provision "shell", inline: <<-SHELL
           curl -sSf https://raw.githubusercontent.com/REPPL/ragged/main/scripts/install.sh | bash
           ragged health
           ragged ingest pdf /vagrant/tests/fixtures/sample.pdf
           ragged query "test query"
         SHELL
       end

       config.vm.define "macos" do |macos|
         macos.vm.box = "yzgyyang/macOS-13"
         # Similar provisioning
       end
     end
     ```
   - Test on **clean VMs** (no prior ragged installation)
   - Verify: Prerequisites → Installation → Usage → Cleanup
   - Document VM testing in `docs/development/testing/vm-testing.md`

4. **Add regression testing** [0.5-1 hour]
   - Test that v0.7.x installations work with documents from v0.6.x:
     - Ingest documents with v0.6.x
     - Upgrade to v0.7.x
     - Verify queries still work
     - Verify embeddings compatible
   - Add `tests/regression/` test suite
   - Run regression tests in CI on version upgrades

5. **Create smoke test suite** [1-1.5 hours]
   - Minimal test suite that validates core functionality:
     ```bash
     # tests/smoke/smoke-test.sh
     #!/bin/bash
     set -e

     echo "1. Prerequisites check..."
     ragged check-prerequisites || exit 1

     echo "2. Health check..."
     ragged health || exit 1

     echo "3. Ingest document..."
     ragged ingest pdf tests/fixtures/sample.pdf || exit 1

     echo "4. Query..."
     ragged query "What is this document about?" || exit 1

     echo "5. List documents..."
     ragged list | grep -q "sample.pdf" || exit 1

     echo "✓ Smoke test passed"
     ```
   - Run smoke test:
     - After every installation
     - In CI pipeline
     - Before releases
   - Add to `scripts/smoke-test.sh`

**Files:**
- `.github/workflows/installation-tests.yml` (new)
- `Vagrantfile` (new - VM testing)
- `tests/regression/` (new directory)
- `tests/smoke/smoke-test.sh` (new)
- `docs/development/testing/vm-testing.md` (new)

**⚠️ MANUAL TEST:**
- Run CI workflow on all matrix combinations
- Verify all tests pass
- Test on real hardware (not just VMs)

**Success Criteria:**
- CI tests pass on all platforms (macOS, Linux, Windows)
- VM testing validates clean installations
- Regression tests ensure upgrade compatibility
- Smoke test catches critical failures
- 100% automated test coverage for installation paths

## QA-003: Performance Benchmarking (4-6 hours)

**Problem:** Users need guidance on which installation method and database mode to choose based on performance requirements.

**Implementation:**

1. **Design benchmark suite** [1-1.5 hours]
   - Define benchmarks:
     - **Installation time:** Time from script start to first query
     - **Ingestion speed:** Documents per second (1k, 10k, 100k documents)
     - **Query latency:** p50, p95, p99 (simple queries, complex queries)
     - **Memory usage:** Resident set size during ingestion and queries
     - **Storage efficiency:** Bytes per document (database size growth)
   - Define test scenarios:
     - Small dataset: 1k documents (personal notes use case)
     - Medium dataset: 10k documents (researcher use case)
     - Large dataset: 100k documents (enterprise use case)
   - Platforms to benchmark: macOS (M1), Linux (x86), Windows (x86)

2. **Implement benchmark scripts** [2-3 hours]
   - Create `benchmarks/installation/`:
     - `benchmark-installation-time.sh` - Measure installation duration
     - `benchmark-ingestion.py` - Measure ingestion speed
     - `benchmark-queries.py` - Measure query latency
     - `benchmark-memory.py` - Monitor memory usage
     - `benchmark-storage.py` - Measure storage efficiency
   - Use consistent test data:
     - `benchmarks/fixtures/` - Sample documents (various sizes)
   - Output results in JSON format:
     ```json
     {
       "platform": "macos-arm64",
       "database_mode": "docker",
       "installation_method": "dmg",
       "installation_time_seconds": 285,
       "ingestion_speed_docs_per_sec": 47.3,
       "query_latency_p95_ms": 142,
       "memory_usage_mb": 1234,
       "storage_bytes_per_doc": 8192
     }
     ```

3. **Run benchmark matrix** [1-1.5 hours]
   - Run benchmarks across all combinations:
     - Platform: macOS (M1), Linux (x86), Windows (x86)
     - Database mode: Docker, embedded
     - Installation method: script, native (DMG/MSI/DEB)
     - Dataset size: 1k, 10k, 100k documents
   - Aggregate results:
     - Calculate means and standard deviations
     - Identify performance outliers
     - Compare Docker vs embedded
     - Compare script vs native installers

4. **Create performance comparison matrix** [1-1.5 hours]
   - Document in `docs/guides/performance-benchmarks.md`:
     ```markdown
     # Performance Benchmarks - v0.7.4

     ## Installation Time

     | Method | macOS (M1) | Linux (x86) | Windows (x86) |
     |--------|------------|-------------|---------------|
     | Script | 5:30 | 6:15 | 7:45 |
     | Native (DMG/MSI/DEB) | 3:45 | 4:20 | 5:10 |

     ## Query Performance (p95 latency, 10k documents)

     | Database Mode | macOS (M1) | Linux (x86) | Windows (x86) |
     |---------------|------------|-------------|---------------|
     | Docker | 120ms | 135ms | 145ms |
     | Embedded | 142ms | 158ms | 165ms |

     **Difference:** Embedded is 15-20% slower than Docker.

     ## Recommendations

     **Use Docker if:**
     - Need maximum performance (large datasets >10k docs)
     - Have Docker available
     - Running on server or desktop

     **Use Embedded if:**
     - Don't have Docker (corporate restrictions, edge devices)
     - Small datasets (<10k docs)
     - Resource-constrained environment
     ```

5. **Add performance recommendations** [0.5-1 hour]
   - Update installation guide with performance guidance:
     - "For best performance, use Docker mode on x86_64 Linux"
     - "Embedded mode suitable for <10k documents or edge devices"
     - "Native installers 30-40% faster than script installation"
   - Add to configuration presets:
     - `config-performance.env` - Optimised for speed (Docker)
     - `config-lightweight.env` - Optimised for resources (embedded)

**Files:**
- `benchmarks/installation/` (new directory)
- `benchmarks/fixtures/` (new directory - test data)
- `docs/guides/performance-benchmarks.md` (new)
- `templates/config-performance.env` (new)

**⚠️ MANUAL TEST:**
- Run benchmarks on all platforms
- Verify results are reproducible
- Validate recommendations match benchmarks

**Success Criteria:**
- Benchmarks run on all platforms (macOS, Linux, Windows)
- Results documented with clear comparison tables
- Recommendations data-driven (based on actual benchmarks)
- Users can choose installation method based on performance needs
- Performance claims validated (e.g., "embedded is 15-20% slower")
