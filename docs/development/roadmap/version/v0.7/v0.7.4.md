# Ragged v0.7.4 Roadmap - WebUI Security Hardening

**Status:** Planned

**Total Hours:** 20-30 hours (AI implementation)

**Focus:** Production-ready security posture for WebUI

**Breaking Changes:** None

**Dependencies:** Requires v0.7.1 completion (or v0.7.3 if collaboration features implemented)

**Purpose:** Secure WebUI against common vulnerabilities before v1.0 production deployment

---

## Overview

Version 0.7.4 implements comprehensive security hardening for the Svelte WebUI, addressing common web vulnerabilities (OWASP Top 10), securing authentication flows, and ensuring production-ready security practices. This version transforms the WebUI from "development prototype" to "production-secure application."

### Problem Statement

**Current Security Gaps:**
- Input validation missing in many forms
- XSS vulnerabilities in user-generated content
- CSRF protection incomplete
- Authentication tokens stored insecurely
- Authorization checks missing in some UI paths
- WebSocket connections unencrypted
- Rate limiting missing on frontend
- Security headers not configured
- Frontend dependencies have known vulnerabilities
- Secrets exposed in frontend configuration

### Target Outcomes

**After v0.7.4 Implementation:**
- ✅ Comprehensive input validation and sanitisation
- ✅ XSS prevention via Content Security Policy
- ✅ CSRF protection on all state-changing requests
- ✅ Secure authentication and session management
- ✅ Authorization enforcement in UI
- ✅ Encrypted WebSocket connections (WSS)
- ✅ Rate limiting on WebUI endpoints
- ✅ Security headers properly configured
- ✅ Zero high/critical vulnerabilities in dependencies
- ✅ Secure secret management

## SEC-001: Input Validation & Sanitisation (3-4 hours)

**Problem:** User input not validated or sanitised; vulnerable to injection attacks and malformed data.

**Implementation:**

1. **Implement input validation library** [1-1.5 hours]
   - Use Zod or Yup for schema validation
   - Define schemas for all forms (document upload, query input, settings, etc.)
   - Validate client-side (UX) and server-side (security)

2. **Add HTML sanitisation** [1-1.5 hours]
   - Use DOMPurify for sanitising user-generated HTML
   - Sanitise all user content before rendering (document titles, comments, annotations)
   - Whitelist safe HTML tags and attributes

3. **Implement file upload validation** [0.5-1 hour]
   - Validate file types (MIME type + magic bytes, not just extension)
   - Limit file sizes (prevent DoS via large uploads)
   - Scan for malicious content (basic checks)
   - Quarantine suspicious files

**Files:**
- `src/webui/lib/validation.ts` (new - validation utilities)
- `src/webui/schemas/` (new - Zod/Yup schemas for all forms)
- `src/web/middleware/validation.py` (new - server-side validation)

**Success Criteria:**
- All forms validate input
- Malicious HTML neutralised
- Invalid file uploads rejected

## SEC-002: XSS Prevention & Content Security Policy (3-4 hours)

**Problem:** Cross-Site Scripting (XSS) vulnerabilities allow attackers to inject malicious scripts.

**Implementation:**

1. **Configure Content Security Policy (CSP)** [1.5-2 hours]
   - Define strict CSP headers:
     ```
     Content-Security-Policy:
       default-src 'self';
       script-src 'self';
       style-src 'self' 'unsafe-inline';  # For Svelte styles
       img-src 'self' data: https:;
       connect-src 'self' wss://localhost;
       font-src 'self';
       object-src 'none';
       base-uri 'self';
       form-action 'self';
     ```
   - Configure CSP reporting endpoint
   - Test CSP doesn't break functionality

2. **Escape user-generated content** [1-1.5 hours]
   - Auto-escape all variables in Svelte templates (default behavior)
   - Use `{@html}` sparingly, only for sanitised content
   - Escape user content in JavaScript contexts

3. **Add XSS detection testing** [0.5-1 hour]
   - Automated XSS payload testing
   - Test common XSS vectors (stored, reflected, DOM-based)

**Files:**
- `src/web/middleware/security_headers.py` (new - CSP and security headers)
- `tests/security/test_xss.py` (new - XSS vulnerability tests)

**Success Criteria:**
- CSP blocks inline scripts
- XSS payloads neutralised
- Zero XSS vulnerabilities found in testing

## SEC-003: CSRF Protection (2-3 hours)

**Problem:** Cross-Site Request Forgery allows attackers to perform actions on behalf of authenticated users.

**Implementation:**

1. **Implement CSRF tokens** [1-1.5 hours]
   - Generate CSRF tokens on session creation
   - Include token in all state-changing requests (POST, PUT, DELETE)
   - Validate tokens server-side before processing

2. **Add double-submit cookie pattern** [0.5-1 hour]
   - Set CSRF token in httpOnly cookie
   - Require matching token in request header
   - Prevents CSRF even if attacker can read cookies

3. **Configure SameSite cookies** [0.5-1 hour]
   - Set `SameSite=Strict` or `SameSite=Lax` on all cookies
   - Prevents cross-origin cookie sending

**Files:**
- `src/web/middleware/csrf.py` (new - CSRF protection)
- `src/webui/lib/csrf.ts` (new - CSRF token handling)

**Success Criteria:**
- CSRF attacks blocked
- Legitimate requests work correctly
- SameSite cookies configured properly

## SEC-004: Authentication Security (JWT & Sessions) (3-4 hours)

**Problem:** JWT tokens and sessions managed insecurely; vulnerable to theft and replay attacks.

**Implementation:**

1. **Secure JWT token storage** [1-1.5 hours]
   - Store JWT in httpOnly cookies (not localStorage)
   - Set secure, httpOnly, SameSite flags
   - Short expiration (15 minutes) with refresh tokens

2. **Implement refresh token rotation** [1-1.5 hours]
   - Issue refresh tokens with longer expiration (7 days)
   - Rotate refresh tokens on each use (one-time use)
   - Revoke old refresh tokens

3. **Add session security** [0.5-1 hour]
   - Bind sessions to IP address (optional, configurable)
   - Detect session hijacking (user agent changes)
   - Force logout on suspicious activity

**Files:**
- `src/web/auth/tokens.py` (modify - secure token management)
- `src/web/auth/sessions.py` (new - session security)

**Success Criteria:**
- Tokens stored securely
- Refresh token rotation works
- Session hijacking detected

## SEC-005: Authorization Enforcement in UI (2-3 hours)

**Problem:** Authorization checks in backend but not consistently enforced in frontend; users can access UI elements they shouldn't.

**Implementation:**

1. **Implement permission-based UI rendering** [1-1.5 hours]
   - Hide UI elements based on user permissions
   - Use Svelte `#if` blocks with permission checks
   - Centralize permission logic in auth store

2. **Add route-level authorization** [0.5-1 hour]
   - Protect routes based on user role
   - Redirect unauthorized users
   - Show 403 Forbidden page

3. **Audit all UI paths** [0.5-1 hour]
   - Review all components for authorization checks
   - Ensure sensitive actions require permissions
   - Test as different user roles

**Files:**
- `src/webui/stores/permissions.ts` (new - permission checks)
- `src/webui/components/PermissionGate.svelte` (new - permission wrapper)

**Success Criteria:**
- UI elements hidden based on permissions
- Unauthorized access blocked
- Permission checks consistent

## SEC-006: Secure WebSocket Connections (WSS) (2-3 hours)

**Problem:** WebSocket connections unencrypted; vulnerable to eavesdropping and tampering.

**Implementation:**

1. **Configure WSS (WebSocket Secure)** [1-1.5 hours]
   - Use `wss://` instead of `ws://`
   - Configure TLS certificates for WebSocket server
   - Enforce secure connections in production

2. **Add WebSocket authentication** [0.5-1 hour]
   - Require JWT token for WebSocket connections
   - Validate token on connection
   - Reject unauthenticated connections

3. **Implement message validation** [0.5-1 hour]
   - Validate all WebSocket messages
   - Sanitise message content
   - Rate limit messages per connection

**Files:**
- `src/web/websocket.py` (modify - add TLS, authentication)
- `src/webui/lib/websocket.ts` (modify - use WSS)

**Success Criteria:**
- WebSocket connections encrypted
- Authentication required
- Messages validated

## SEC-007: Rate Limiting on Frontend (2-3 hours)

**Problem:** No rate limiting on frontend actions; vulnerable to abuse and DoS.

**Implementation:**

1. **Implement client-side rate limiting** [1-1.5 hours]
   - Debounce query inputs (prevent rapid queries)
   - Throttle API calls (max requests per minute)
   - Queue requests if rate limit exceeded

2. **Add server-side rate limiting** [0.5-1 hour]
   - Rate limit by IP address and user ID
   - Different limits for different endpoints (stricter for expensive operations)
   - Return 429 Too Many Requests

3. **Show rate limit feedback to user** [0.5-1 hour]
   - Display "Rate limit exceeded, please wait..." message
   - Show countdown timer until next request allowed
   - Suggest optimizing query patterns

**Files:**
- `src/webui/lib/rate-limiter.ts` (new - client-side rate limiting)
- `src/web/middleware/rate_limit.py` (new - server-side rate limiting)

**Success Criteria:**
- Rapid requests throttled
- Users informed of rate limits
- DoS attacks mitigated

## SEC-008: Security Headers Configuration (1-2 hours)

**Problem:** Security headers missing; browser protections not enabled.

**Implementation:**

1. **Configure all security headers** [1-1.5 hours]
   ```
   Strict-Transport-Security: max-age=31536000; includeSubDomains
   X-Content-Type-Options: nosniff
   X-Frame-Options: DENY
   X-XSS-Protection: 1; mode=block
   Referrer-Policy: strict-origin-when-cross-origin
   Permissions-Policy: geolocation=(), microphone=(), camera=()
   ```

2. **Test header configuration** [0.5-1 hour]
   - Verify headers sent on all responses
   - Test with security scanning tools (SecurityHeaders.com)
   - Achieve A+ rating

**Files:**
- `src/web/middleware/security_headers.py` (modify - add all headers)

**Success Criteria:**
- All security headers configured
- A+ rating on SecurityHeaders.com
- No warnings from browser security tools

## SEC-010: Secure Secret Management (2-3 hours)

**Problem:** Secrets (API keys, tokens) exposed in frontend configuration or source code.

**Implementation:**

1. **Remove secrets from frontend code** [1-1.5 hours]
   - Audit codebase for hardcoded secrets
   - Move secrets to backend environment variables
   - Use proxy endpoints for API calls requiring secrets

2. **Implement secure configuration** [0.5-1 hour]
   - Use `.env` files (never committed to git)
   - Inject secrets at build time (not runtime)
   - Rotate secrets regularly

3. **Add secrets scanning** [0.5-1 hour]
   - Use tools like `git-secrets` or `trufflehog`
   - Scan commits for accidentally committed secrets
   - Block commits containing secrets

**Files:**
- `.github/workflows/secrets-scan.yml` (new - automated secrets scanning)
- `src/webui/config.ts` (modify - remove hardcoded secrets)

**Success Criteria:**
- No secrets in frontend code
- Secrets properly managed in backend
- Automated scanning prevents accidental commits

## Known Risks

- **Performance overhead:** Security measures may add latency (mitigate: optimize validation, caching)
- **False positives:** XSS/CSRF protection may block legitimate requests (mitigate: testing, whitelisting)
- **Breaking changes:** Dependency updates may introduce bugs (mitigate: thorough testing)
