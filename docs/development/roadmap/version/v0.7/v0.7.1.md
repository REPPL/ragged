# Ragged v0.7.1 Roadmap - Post-Launch Refinements & User Feedback

**Status:** Planned

**Total Hours:** 15-25 hours (AI implementation)

**Focus:** Refine installation based on real user experiences

**Breaking Changes:** None

**Dependencies:** Requires v0.7.0 completion and 2-4 weeks of user feedback

**Purpose:** Address gaps and pain points discovered after v0.7.0 release

---

## Overview

Version 0.7.1 is a refinement release that addresses real-world installation issues discovered through user feedback and installation analytics. Rather than pre-emptively solving hypothetical problems, this version responds to actual user experiences with v0.7.0.

**Rationale:** Initial releases always reveal edge cases, platform-specific issues, and user expectations that weren't anticipated. v0.7.1 closes these gaps to achieve >98% installation success rate.

---

## REFINE-001: Installation Analytics (Opt-in, Privacy-Preserving) (5-7 hours)

**Problem:** Without usage data, we can't identify which installation steps cause the most failures or how users actually install ragged.

**Implementation:**

1. **Design telemetry system** [1.5-2 hours]
   - Define metrics to track:
     - Installation method chosen (CLI/Docker/Dev)
     - Installation success/failure at each step
     - Time spent per installation step
     - Platform (macOS/Linux/Windows) and Python version
     - Prerequisites check results
   - Privacy requirements:
     - No personally identifiable information (PII)
     - Hashed system identifiers (one-way hash)
     - Local-only storage with optional aggregated upload
     - Explicit opt-in (never opt-out)
   - Design aggregation strategy (local → anonymised aggregate)

2. **Implement telemetry collection** [2-3 hours]
   - Create `src/telemetry/collector.py`:
     - Event tracking (installation step start/complete/fail)
     - Duration tracking for each step
     - Error type classification
   - Store events in `~/.ragged/telemetry/events.json`
   - Add telemetry hooks to installation scripts
   - Add telemetry to v0.7.0 INSTALL features (health checks, welcome, etc.)

3. **Add opt-in mechanism** [1-1.5 hours]
   - Prompt during installation: "Help improve ragged by sharing anonymous installation data? [y/N]"
   - Environment variable: `RAGGED_TELEMETRY=enabled|disabled`
   - CLI command: `ragged telemetry enable/disable/status`
   - Show what data is collected: `ragged telemetry show-data`
   - Allow review before sending: `ragged telemetry review`

4. **Create analytics dashboard (local)** [0.5-1 hour]
   - Command: `ragged telemetry stats` shows local aggregates
   - Display:
     - Installation success rate
     - Average time per step
     - Most common failures
     - Platform distribution
   - Export to JSON for sharing: `ragged telemetry export --anonymise`

**Files:**
- `src/telemetry/collector.py` (new)
- `src/telemetry/__init__.py` (new)
- `src/commands/telemetry.py` (new)
- `scripts/install.sh` (modify - add telemetry hooks)
- `.env.example` (add RAGGED_TELEMETRY option)

**⚠️ MANUAL TEST:** Enable telemetry, run installation, verify data collected is anonymous

**Success Criteria:**
- Telemetry is opt-in only (never auto-enabled)
- No PII collected (verified by inspection)
- Users can review data before sharing
- Analytics help identify top 3 installation pain points
- >30% of users opt in (industry standard for developer tools)

## REFINE-002: Enhanced Error Recovery (4-6 hours)

**Problem:** v0.7.0 errors, whilst improved, still don't cover all edge cases discovered by real users.

**Implementation:**

1. **Analyse v0.7.0 error patterns** [1-1.5 hours]
   - Review GitHub issues tagged "installation"
   - Review support requests
   - Analyse telemetry data (if available)
   - Identify top 10 most common errors not covered by v0.7.0

2. **Expand error message database** [2-3 hours]
   - Add error handlers for discovered edge cases:
     - Python virtual environment conflicts
     - Firewall blocking Ollama/ChromaDB
     - Disk space issues (insufficient for models)
     - Network timeouts during model downloads
     - Permission errors on macOS (SIP, Gatekeeper)
     - Windows-specific PATH issues
     - WSL-specific Docker issues
   - Each error includes:
     - Clear description in plain English
     - Specific recovery action
     - Link to troubleshooting section
     - Estimated time to fix

3. **Add auto-recovery for common issues** [1-1.5 hours]
   - Disk space: Suggest `ragged cache clear` to free space
   - Port conflicts: Offer to change ports automatically
   - Missing dependencies: Offer to install (with permission)
   - Permission errors: Provide exact `chmod`/`chown` command
   - Network timeouts: Offer to retry with exponential backoff

4. **Expand troubleshooting matrix** [0.5-1 hour]
   - Add discovered edge cases to `docs/guides/troubleshooting.md`
   - Link error messages to specific matrix entries
   - Add "Community Solutions" section for user-contributed fixes

**Files:**
- `src/errors/handlers.py` (modify - add new error handlers)
- `src/errors/recovery.py` (new - auto-recovery logic)
- `docs/guides/troubleshooting.md` (modify - expand matrix)

**⚠️ MANUAL TEST:** Trigger each new error condition, verify recovery suggestions are actionable

**Success Criteria:**
- Error messages address 95%+ of reported issues (from v0.7.0 feedback)
- Auto-recovery works for 50%+ of common errors
- Users can self-resolve 80%+ of installation issues without support
- Support requests for covered errors reduce to near-zero

## REFINE-003: Installation Resume/Checkpoint System (3-5 hours)

**Problem:** If installation fails at step 8 of 10, users must restart from step 1, wasting time and causing frustration.

**Implementation:**

1. **Design checkpoint system** [1-1.5 hours]
   - Define checkpoints in installation process:
     1. Prerequisites validated
     2. Repository cloned
     3. Virtual environment created
     4. Dependencies installed
     5. Configuration generated
     6. Services started
     7. Models downloaded
     8. Health check passed
     9. Welcome experience completed
   - Define checkpoint storage format (JSON)
   - Design resume logic (skip completed steps)

2. **Implement checkpoint tracking** [1.5-2 hours]
   - Create `~/.ragged/install-checkpoints.json`:
     ```json
     {
       "installation_id": "uuid",
       "started_at": "2025-01-15T10:00:00Z",
       "last_checkpoint": "dependencies_installed",
       "checkpoints": {
         "prerequisites_validated": {"completed": true, "timestamp": "..."},
         "repository_cloned": {"completed": true, "timestamp": "..."},
         "dependencies_installed": {"completed": true, "timestamp": "..."},
         "configuration_generated": {"completed": false},
         ...
       }
     }
     ```
   - Add checkpoint markers to installation scripts
   - Track timestamp and status for each checkpoint

3. **Add resume functionality** [0.5-1 hour]
   - Detect interrupted installation on restart
   - Prompt: "Previous installation detected. Resume from 'dependencies_installed'? [Y/n]"
   - Add `--resume` flag: `./install.sh --resume`
   - Add `--restart` flag: `./install.sh --restart` (ignore checkpoints, start fresh)
   - Skip completed checkpoints when resuming

4. **Add checkpoint management commands** [0.5-1 hour]
   - `ragged install status` - Show installation progress
   - `ragged install resume` - Resume interrupted installation
   - `ragged install reset` - Clear checkpoints (start fresh)

**Files:**
- `scripts/install.sh` (modify - add checkpoint tracking)
- `src/commands/install.py` (new - install management)
- `~/.ragged/install-checkpoints.json` (generated)

**⚠️ MANUAL TEST:** Interrupt installation at various checkpoints, verify resume works correctly

**Success Criteria:**
- Resume works from any checkpoint
- No data loss during interruption
- Time saved: Resume reduces reinstall time by 50-80%
- Users can restart fresh if needed (`--restart`)

## REFINE-004: Configuration Migration Tools (3-5 hours)

**Problem:** Upgrading ragged versions may overwrite user customisations, requiring manual reconfiguration.

**Implementation:**

1. **Design migration system** [1-1.5 hours]
   - Define migration strategy:
     - Detect old configuration (check version in `.env`)
     - Create backup before migration
     - Preserve user customisations
     - Apply new defaults for new settings
     - Validate migrated configuration
   - Design version-specific migration rules
   - Handle edge cases (corrupted config, missing required fields)

2. **Implement configuration migration** [1.5-2 hours]
   - Create `src/config/migration.py`:
     - `migrate_config(from_version, to_version)` - Main migration function
     - `backup_config()` - Create timestamped backup
     - `merge_configs(old, new)` - Preserve user values, add new defaults
     - `validate_config(config)` - Ensure migrated config is valid
   - Support migration paths:
     - v0.6.x → v0.7.0
     - v0.7.0 → v0.7.1
     - Future versions
   - Handle renamed variables:
     - `OLD_VAR_NAME` → `NEW_VAR_NAME` (with warning)
   - Handle removed variables:
     - `DEPRECATED_VAR` → Remove (with notification)

3. **Add migration CLI commands** [0.5-1 hour]
   - `ragged config migrate` - Auto-detect version and migrate
   - `ragged config migrate --from 0.6.0 --to 0.7.1` - Explicit versions
   - `ragged config backup` - Manual backup before changes
   - `ragged config restore <backup-file>` - Restore from backup
   - `ragged config diff` - Show differences between current and default

4. **Add automatic migration on upgrade** [0.5-1 hour]
   - Detect version change on ragged startup
   - Prompt: "Configuration version mismatch. Migrate now? [Y/n]"
   - Run migration automatically if user confirms
   - Show what was changed (diff summary)

**Files:**
- `src/config/migration.py` (new)
- `src/config/settings.py` (modify - add version detection)
- `src/commands/config.py` (modify - add migration commands)
- `~/.ragged/config-backups/` (generated - timestamped backups)

**⚠️ MANUAL TEST:** Upgrade from v0.7.0 with customised config, verify customisations preserved

**Success Criteria:**
- Configuration migration works for 100% of users
- User customisations preserved during upgrade
- New settings get sensible defaults
- Backup created before migration (recovery possible)
- Migration warnings clear and actionable

## Known Risks

- **Telemetry resistance:** Users may be suspicious of analytics (mitigate: explicit opt-in, show data)
- **Platform-specific errors:** Edge cases vary widely by platform (mitigate: community contributions)
- **Resume complexity:** Checkpoint system adds state management complexity (mitigate: thorough testing)
- **Migration edge cases:** Configuration conflicts may be difficult to resolve automatically (mitigate: manual override option)

## Implementation Notes

### When to Implement v0.7.1

**Criteria:**
- v0.7.0 has been released and used by 50-100 users
- 2-4 weeks have passed (enough time for feedback)
- GitHub issues/discussions reveal patterns in installation problems

**Data sources for prioritisation:**
- GitHub issues tagged "installation"
- Support requests (if support channel exists)
- Community feedback (Discord, discussions)
- Telemetry data (if users opted in during v0.7.0)

**Recommended approach:**
1. Release v0.7.0
2. Wait 2-4 weeks for feedback
3. Analyse top installation pain points
4. Adjust v0.7.1 scope based on findings (may add/remove features)
5. Implement v0.7.1 with highest-impact fixes
