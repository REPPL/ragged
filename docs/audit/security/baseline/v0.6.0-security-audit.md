## Executive Summary

ragged v0.6.0 demonstrates a **strong security posture** with comprehensive implementation of enterprise-grade security controls across web UI, API, and data storage layers. The project shows evidence of security-first design with multiple layers of defence, encryption at rest, input validation, and privacy-by-default architecture.

### Overall Risk Rating: **LOW-MEDIUM**

**Key Strengths:**
- Comprehensive middleware security stack (8 layers)
- Encryption at rest with secure key management
- Strong input validation framework
- Privacy-first architecture (local-only by default)
- Active security testing (100+ security tests)
- Recent critical vulnerability fixes (pickle removal, path traversal, network isolation)

**Priority Concerns:**
1. **MEDIUM**: Session storage scalability (in-memory, no persistence)
2. **MEDIUM**: MIME type validation (basic magic byte detection)
3. **MEDIUM**: JWT middleware disabled by default (authentication opt-in model)
4. **LOW**: Temporary file handling race conditions
5. **LOW**: Plugin sandbox enforcement verification needed

## 2. Security Architecture Overview

### 2.1 Defence-in-Depth Layers

ragged implements a comprehensive defence-in-depth strategy:

```
Layer 1: Network Isolation (127.0.0.1 binding by default)
Layer 2: CORS Configuration (explicit whitelist)
Layer 3: Rate Limiting (token bucket algorithm)
Layer 4: Request Validation (size, Content-Type, JSON depth)
Layer 5: Authentication (optional JWT)
Layer 6: Session Security (timeout, CSRF tokens)
Layer 7: Input Sanitisation (XSS pattern detection)
Layer 8: Response Sanitisation (header removal, error scrubbing)
Layer 9: Encryption at Rest (Fernet AES-128 + HMAC)
Layer 10: Plugin Sandboxing (resource limits, permission system)
```

### 2.2 Middleware Stack Architecture

**FastAPI Middleware Order** (src/web/api.py:57-126):
```
Request Flow:
1. ResponseSanitizationMiddleware → (outermost)
2. SecurityHeadersMiddleware (CSP, HSTS)
3. APIVersionMiddleware
4. RequestValidationMiddleware
5. JWTSecurityMiddleware (optional, disabled)
6. SessionSecurityMiddleware
7. XSSProtectionMiddleware
8. CORSMiddleware → (innermost)
→ Application Endpoints

Response Flow:
← CORSMiddleware (innermost)
← XSSProtectionMiddleware
← SessionSecurityMiddleware
← JWTSecurityMiddleware
← RequestValidationMiddleware
← APIVersionMiddleware
← SecurityHeadersMiddleware
← ResponseSanitizationMiddleware (outermost)
```

**Critical Observation**: Middleware ordering is correct (response sanitisation outermost ensures all errors are sanitised before reaching client).

#### H-2: Session Storage Scalability & Persistence

**Location**: `src/web/middleware/security.py:160`

**Description**:
Sessions stored in-memory (`self._sessions: dict[str, dict[str, Any]] = {}`). No persistence mechanism. Lost on service restart. Vulnerable to memory exhaustion with many concurrent users.

**Risk Assessment**:
- **Severity**: MEDIUM
- **Likelihood**: LOW (local-only deployment)
- **Impact**: DoS via session exhaustion, UX degradation on restart

**Evidence**:
```python
class SessionSecurityMiddleware(BaseHTTPMiddleware):
    def __init__(self, app: ASGIApp, session_timeout: int = 3600, ...):
        super().__init__(app)
        self._sessions: dict[str, dict[str, Any]] = {}  # In-memory only
```

**Recommendation**: **MEDIUM** priority. Implement Redis backend for production deployments. Add session count monitoring.

#### H-3: MIME Type Validation Insufficient

**Location**: `src/utils/security.py:98-155`

**Description**:
Basic magic byte detection without `python-magic` library. Could miss sophisticated file type masquerading attacks.

**Code Analysis**:
```python
def validate_mime_type(file_path: Path, expected_types: list[str] | None = None) -> str:
    # Read first few bytes to detect file type
    with open(file_path, "rb") as f:
        header = f.read(8)  # Only 8 bytes!

    # Basic magic byte detection (simplified)
    if header.startswith(b"%PDF"):
        mime_type = "application/pdf"
    # ... limited coverage
```

**Limitations**:
1. Only checks first 8 bytes (some exploits hide malicious content deeper)
2. No comprehensive signature database
3. ZIP-based formats treated generically (potential for macro exploits)

**Risk Assessment**:
- **Severity**: MEDIUM
- **Likelihood**: LOW (requires targeted attack)
- **Impact**: Malicious file execution, XSS via crafted documents

**Recommendation**: **HIGH** priority. Integrate `python-magic` library for robust MIME detection. See change request CR-SEC-001.

### 3.3 MEDIUM Findings

#### M-1: Temporary File Handling Race Conditions

**Location**: `src/web/api.py:372-437`

**Description**:
Temporary files created with `tempfile.NamedTemporaryFile(delete=False)` and manually deleted in `finally` block. Small window for race condition attacks.

**Code**:
```python
with tempfile.NamedTemporaryFile(delete=False, suffix=file_ext) as temp_file:
    temp_file.write(content)
    temp_path = Path(temp_file.name)

try:
    # ... processing ...
finally:
    if temp_path.exists():
        temp_path.unlink()  # Race window here
```

**Potential Attack**: Attacker with local access could:
1. Monitor `/tmp` for new files
2. Create symlink with same name before `unlink()`
3. Potentially cause deletion of unintended files

**Risk Assessment**:
- **Severity**: MEDIUM
- **Likelihood**: LOW (requires local access + timing)
- **Impact**: Information disclosure, unintended file deletion

**Recommendation**: **LOW** priority. Current implementation is acceptable for local-only deployment. For hardening, use `tempfile.TemporaryDirectory()` context manager.

#### M-2: ChromaDB NoSQL Injection Surface

**Location**: `src/storage/chromadb_store.py:306-362` + `src/storage/metadata_serializer.py`

**Description**:
ChromaDB `where` clause construction from user-controlled metadata could allow filter manipulation. Metadata serialiser provides protection but needs validation.

**Code Path**:
```python
def query(self, query_embedding, k=5, where: dict[str, Any] | None = None):
    # 'where' parameter passed directly to ChromaDB
    results = self.collection.query(
        query_embeddings=query_list,
        n_results=k,
        where=where,  # Potential injection point
    )
```

**Protection Mechanisms**:
1. **Metadata Serialisation** (metadata_serializer.py:18-84):
   - Strict type validation (str/int/float/bool only)
   - Complex types serialised to JSON with `__json__:` prefix
   - Size limits (100KB per field)
   - Depth limits (max 10 levels nesting)

2. **Validation** (utils/validation.py): Comprehensive input validation framework

**Testing Evidence**:
- `tests/security/test_nosql_injection.py` contains dedicated injection tests
- Tests passed in audit (no failures in NoSQL injection suite)

**Risk Assessment**:
- **Severity**: MEDIUM
- **Likelihood**: LOW (strong validation in place)
- **Impact**: Unauthorised data access, filter bypass

**Recommendation**: **ACCEPT WITH MONITORING**. Current protections are adequate. Add additional validation for `where` clause structure if exposing to external APIs.

import magic

def validate_mime_type(file_path: Path, expected_types: list[str] | None = None) -> str:
    mime = magic.Magic(mime=True)
    detected_type = mime.from_file(str(file_path))

    if expected_types and detected_type not in expected_types:
